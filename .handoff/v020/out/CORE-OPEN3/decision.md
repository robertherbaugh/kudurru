# CORE-OPEN3 decision row (D378, complete corrected row)

This replaces the D378 row of `out/CORE-APPLY-OPEN/decision.md` as a whole.

| D378 | Requests with several items on the node that owns the commits | On the complete SQLite runtime `POST /apply` and `POST /{kind}:batchDelete` still run one current command for each item with the request's original credential, lease, elected writer episode and lifetime, and declare one command chain of the provider coordinator for the request (`ObjectItems`). Until one of the request's commands has completed, each is admitted on the original lease exactly as a single command is. The first completed command anchors the chain: on its own commit receipt, which the Store issues in the command's finalizer under the writer lock (`sqlite.CommandReceipt`), or, when it changed nothing, on the coordinator's mark at that moment. Every later command is admitted under the publication gate only while the coordinator's mark of the last command that changed canonical state is still the chain's anchor, compared by identity; it also requires the original writer episode and a Store authority equal to the lease's own in every field except an advanced installed revision, and it reads the raw credential, grants, ownership, preconditions and limits again in its transaction. A foreign commit is a state-changing command of anyone else through the coordinator: a public API mutation under any credential, including a sign-in, a member command forwarded from a follower, an operator-started integration operation, a migration step or the unblock-request sweep; a command whose SQL outcome is unknown counts as one. Writers outside the coordinator, which take only the Store lock or the primary pin, are not detected and do not stop a request: the node's own follow-up work (status reconciliation, the zone lifecycle and its heads, list fetch status, integration reconciliation, the RoleBinding objects source, the login-lane request charge and provider authority admission) and two writers that act for another party, RFC 2136 updates under a TSIG key and commands of the local admin socket. This is accepted as the rule: each item reads everything it is admitted on again in its own transaction, so an undetected write can change only what a later item finds, never what it is decided on. Replacements of node-local dependency installations between two items are not compared either; each command pins the current ones. DNS does not wait for the request: an ordinary query answer from local, authoritative or mixed data is bound to the publication that is served (`Publisher.Serves`, by identity of the root seal) instead of to the latest commit, or to full data currency when that still holds, and its dependency check (`RuntimeOwner.DNSDependenciesCurrent`) covers only what DNS answers are computed from (the root lifetime, the DNS keyring, the transferred and catalog zone data and the anchor input), not the provider host, the license cut or the provider resource set that only HTTP authentication uses; a published successor retires the old answers at once, and transfers, UPDATE acknowledgments, API dig, cache insertions and native resolver mutations keep full data currency. API writes do not wait for publication, so right after an acknowledged write DNS answers the previous data (`NXDOMAIN` for a new name) until the node publishes, and for as long as it cannot publish, deleted records and zones included; readiness then reports `prepare_failed` and the log says `complete serving generation not published`. Every commit still retires the publication that every other API request is bound to, so before a later item the request lets the node publish: it waits, inside the request's lifetime and writer episode, until the publisher is current again (`Publisher.WaitTerm`), and then commits nothing for 200 milliseconds. It does so after two seconds of work since the node last had a current publication for it, and at once when another caller's read (`GET` or `HEAD`) waits in the HTTP listener's two-second capture wait (`Publisher.AwaitHTTP`), as long as the request has not spent longer in its waits than in its own work; a waiting write is not counted. The mark is set before authentication, so any client's `GET` or `HEAD`, signed in or not, makes the request yield; the credit bounds what that costs. A read is served only when one publication completes within its capture wait; while one publication takes longer, reads during the request are still refused with `generation_pending`. The whole-image work that every reader of one generation repeats is remembered by exact input bytes (`internal/store/replication/memo.go`): the payload digest by the SHA-256 of the encoding it hashes, each object's identity of at most 4 KiB by the SHA-256 of its document (up to 131,072 entries and 32 MiB, so an image of the default 100,000 objects fits), and the canonical encoding of the last two complete images of at most 8 MiB by the SHA-256 of a fixed-width depth bound followed by their bytes; errors are never remembered, each cache is bounded by entry count and by bytes and evicts random entries when full (a working set above the bound still gets a share of hits), and a hit returns what the uncached function returned for the same bytes and depth. Identities are remembered when an object is decoded, before its image is validated, so objects of a rejected image can be remembered too, within the same bounds. Each new generation is still canonicalized and digested once, and each owner still decodes the image and runs its own object and entry checks. The wait is bounded: two seconds at first, doubled after a wait that ended without a publication, twice the last publication's time after one that came, at most ten seconds, and the work between two timed waits is at least the next bound. A wait that reaches its bound goes on without the publication and without the rest, so the pace makes a request at most about twice as slow and cannot by itself run it out of its lifetime; the wait captures no lease and admits nothing, so the chain compare still decides and a foreign commit in the pause stops the rest. After a foreign commit every later item answers `unavailable` ("another change was committed on this node while the request ran"), is not applied and is never admitted again; earlier items stay committed. An item reached after the request's lifetime ended answers `unavailable` with that cause. A follower keeps D375: it forwards each item as its own member command and never uses the chain. Kubernetes has no such gate and is unchanged. | Every commit retires the lease that the next command's admission compares against, so one request applied only its first new or changed document and refused the rest with `unavailable` ("current writable serving generation unavailable"): a three-document `kudurru apply`, an eight-document `kudurru restore` into a new node and the dashboard's multi-delete each needed one run per document (mounted reproduction retained). No item is decided from the request's image: everything an item is admitted on is read in its own transaction. What the lease comparison added between two items is that nobody else had acted; an exact compare of command receipts keeps that for every command through the coordinator, but not for the writers outside it listed above. The node follows each commit with its own status and lifecycle writes within milliseconds and replaces provider resource sets on its own schedule, so a compare against the exact generation of the previous item, or against the lease's dependency installations, cuts a request at an arbitrary item (a mounted restore stopped at its fifth document). Unpaced, the items of one request commit back to back and the node has no current publication for the whole request: in a review probe on a loaded machine one apply of 300 documents left an existing local record unanswered for 27.5 s and other callers got `503 generation_pending`. A pace alone did not fix DNS: under the race detector a publication of 120 record sets took 1 to 10 s, the node published rarely, and every replacement of the provider resource set (its worker, provider authority admission, a reset) withheld local answers until the next publication, so one apply of 120 documents left the record unanswered for 80 s with a fixed pace and still for up to 7 s with an adaptive one. Bound to the served publication and to its DNS dependencies, the same apply kept the longest gap between answers at 0.8 s without and 0.13 s with the race detector; the 0.8 s was the zone answering SERVFAIL while its lifecycle receipt still named the DNSZone's previous resourceVersion after the status write of a new serial, which the status-write row (56637cec) removed: with it the gap stayed at most 81 ms in 27 of 28 runs without the race detector and at most 145 ms in 10 runs pinned to two CPUs (with the earlier image.go put back, the gaps came back at 0.30 and 0.66 s in 2 of 8 runs, and with the SERVFAIL assertion 4 of 8 runs failed on 3 to 12 SERVFAIL answers; one run at the fix had an unexplained 1.39 s gap without any SERVFAIL, about 1 in 100 runs, which stays open, and the test now reports what the probes got in such a gap), and the mounted test now fails on any SERVFAIL as well as on a gap above one second. Reads need an eligible publication for their credentials and data, so they cannot use a stale one; the pace after a fixed work budget left a read waiting past its two-second capture wait (41 of 43 refused), while yielding to a waiting read served every read without the race detector (6 s for 120 documents); under the race detector, where one publication reaches ten seconds, most reads are still refused. A profile of that run put about a third of the attributable CPU in `replication` Validate, Decode, Seal and Digest, repeated by each reader of a generation; remembering their pure parts by input bytes cut that share by about 30 % and total CPU by about 18 %, but reads under the race detector stay mostly refused (43 of 58), because the rest is per-generation decoding and per-owner validation and race-detector overhead outside them. Serving DNS from the served publication is what a follower does from its last pull and what the node already did for recursive answers; nothing is decided from it. | Capturing a new lease for each item, as migration programs do (D223) (waits for one complete publication per item and admits an item after any foreign commit); admitting item N+1 only at exactly the generation that item N produced (the node's own writes follow every commit and the publisher skips generations, so that generation is rarely published); tolerating any commit after the request's first one (a foreign decision between two items would go unnoticed);
