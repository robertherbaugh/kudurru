| D367 | Integration `deletionPolicy: Delete` cleanup lifecycle | An Integration whose policy is `Delete` carries the reserved finalizer `kudurru.io/integration-cleanup`, so every delete path (a removed file document, `kubectl delete`) leaves a readable terminating object with its spec, credential references, UID and status; no tombstone kind or delete API is added. SQLite admission arms the finalizer in the same write as the spec, and no manager's apply, `Force` included, can set or strip it. A live `Delete` object that is stored without it is paused (`CleanupFinalizerMissing`), and the SQLite root refuses every effect of such an instance inside its transaction, so nothing is owned unarmed. Kubernetes has no kudurru admission: once a host runs there (DEL-8; none does in v0.2), the elected host is to arm it with an exact-resourceVersion metadata patch before any ledger intent, and the driver carries it through `Force` takeovers. Each job holds one mode (normal, cleanup, release), derived from the captured object and re-checked by root against the object read at every effect; a change of mode cancels and joins the job before its successor is elected on the same per-instance key. The cleanup job repeats bounded runs on fresh frames, each taking a concurrency slot only while it runs. A run resolves pending intents from a complete reread and then deletes, through the unchanged intent, fence, budgeted request, receipt and confirm path, only record sets whose rows all carry this cluster and UID marker, whose provider IDs are all in the confirmed ledger baseline, and whose name has no conflict. For those, `Delete` overrides per-zone and ledger-retained `upsert-only` and `create-only`. A partially applied delete is resumed in cleanup even after the credential or configuration changed; any other partially applied intent stays pending, because nothing is desired any more. A ledger row is forgotten by exact UID and version only when it has no pending operation and its record is absent (a confirmed delete, or a fresh complete observation that holds none of its provider IDs and no marked row at its key). Then one fenced transaction purges the local state of the instance's source (source-owned record sets and zones, source head and chunks, name allocations, deliveries, inventory clients) and, once the published state shows none of it, another verifies that nothing of the incarnation remains, removes the finalizer by exact UID and resourceVersion and writes an audit summary (on Kubernetes, with DEL-8, sequential exact-identity deletes). Operation history, which nothing prunes while an instance lives, is never held or committed whole: a ledger row leaves with a bounded batch of its operations, and the rest go a stored page at a time once no ledger row is left; a bounded read that meets more than it admits decides nothing and reports `CapacityExceeded`. A run that its bound cuts inside such a commit without any progress halves the lease's commit size, and a run that made progress yields before its bound would cut its next commit, so a slow store slows the cleanup but cannot stall it. What bounds a history is the SQLite store itself: root's capture reads a whole generation, which refuses more than 100,000 objects or 256 MiB of all kinds (the replication image limits), so the purge and finalization scan bound of 200,000 rows of one kind is never reached first. Proven record sets are deleted even while others block, but nothing is finalized while a conflict, a marker without ledger evidence, ledger provider IDs that still exist without the marker, rows of a destination no longer in the spec, an uncertain receipt or leftover local state remains; each is reported with a specific reason and counts and re-evaluated at the resync interval, at most every ten minutes. Suspension and an expired license pause the cleanup without provider I/O; a missing credential pauses only the cleanup of a publisher, since an inbound instance owns nothing at its provider and its cleanup makes no provider call. A terminating object that carries the finalizer under any other policy is released: SQLite admission does so in the apply that changes the policy, and the host's release job, which needs no license, credential or provider, does so for state no apply stored. The shared request budget row is never deleted. The operator's surface: integration summaries carry `deletionPolicy`, `terminating` and `deletionRequestedAt` from the stored object and, while the host's status for that revision is `Terminating`, its `remaining`, `blocked` and `uncertain` counts; check, preview, sync and act on a terminating instance are `409`. The reviewed release command (`POST /integrations/{namespace}/{name}/release`, `kudurru integrations release NAME --uid --revision`) is root's: it needs a new permission `integrations.release` (admin only, because it abandons a promise that sync and act cannot), binds the reviewed UID and resource version both in the request's published snapshot and in its one current command, admits only an object that is being deleted and carries the finalizer, re-authorizes the original credential in that command, removes the finalizer with the exact-identity `UpdateFinalizer` and records `integration.release` with the counts it retained. It does not rewrite the spec to `Retain`, needs no license, credential or provider, runs only on the elected writer and takes no per-instance lease: a cleanup run is fenced at its next effect, and a provider request already in flight leaves its ledger row pending, like any released incarnation. | `Delete` was refused (D239) because treating it as `Retain` silently breaks the operator's promise, and `Retain` leaves records that a recreated Integration, which has a new UID, can never adopt. A finalizer is the one durable tombstone both stores already honor; it keeps the credential reference (D197) and a status surface on the public object and covers the only SQLite delete path. A marker can be copied with a record and a ledger row can outlive a record someone took over, so both must agree before anything is deleted (D206). Budgets and fences must survive rotation and failover (D209), and deletes bind original identity (D291, D302). A complete image may never hold a source head without its chunks or allocation evidence without its allocation, which makes the local purge one transaction. An operator must always be able to end a terminating object without the provider, the credential or the license. An operator who removed the document, lost the credential or the license, or meets a conflict that cannot be resolved must be able to end the cleanup from the API without editing a file, and the review binding is the one every other integration command uses (D291). | A private tombstone kind (a second copy of credential references, no public status, diverging drivers); synchronous cleanup inside one reviewed delete command (misses file removal and `kubectl delete`, cannot fit large zones in the operation bound); deleting on marker alone or on ledger evidence alone; honoring `upsert-only` or `create-only` during cleanup; finishing a partially applied create or update only to delete it; finalizing partially or over an unresolved receipt; deleting nothing until every record set is provable (a late conflict would undo it anyway); requiring a credential and a reachable controller to purge local state; holding a concurrency slot while blocked; a fixed Forget size whatever the store's speed (a commit that cannot finish in the run bound is cut at the same place every run); arming in the Kubernetes driver's Apply, which nothing clears while no host runs there; deleting or resetting the request budget; keeping the refusal; releasing by a spec change to `Retain` from the API (it must write as the file reconciler's manager or take the object over with `Force`, and rewrites what the operator declared, while the metadata-only exact-identity finalizer removal is the write the cleanup itself uses); reusing `integrations.sync` or `integrations.delete` for the release; taking the per-instance lease for a release (a held or blocked cleanup would then also hold the release) |
