| D377 | What a node answers across a canonical commit: upstream failures and native recursion | Two parts. (1) D332's retained class also covers the empty SERVFAIL of an ordinary query whose upstream was actually asked and failed or timed out: status `servfail_upstream` or `timeout_upstream`, origin unattributed, response code SERVFAIL, AA clear, empty answer and authority sections, at most OPT in the additional section, and the internal `pipeline.Response.UpstreamContacted` evidence. Only the upstream stage sets that evidence, from its group exchange's `upstream.Error.Attempted` (a forwarder was sent the query, or the native resolver sent a query to at least one authority; the resolver records that itself and marks an error `recursor.IsAdmission` only when no authority was asked, and the mark survives the end of the query). A refusal the node produces without asking a server is not in the retained class: a failed serving capture in `Stage.Bind`, a refused native recursion or cache admission, a query that ended before any server was tried, indeterminate DNSSEC validation, failed rewrite targets, stub-zone and other failure-origin answers. As an ordinary query response it follows D378's served-publication policy: sent while its publication is served, including after an unpublished commit, and withheld once a successor is published. Only a contacted upstream failure is still sent after that. The dependency, anchor, single-attempt and no-transfer checks of the retained path are unchanged. (2) Native recursion starts and takes each per-acquisition cache attempt under the retained recursive policy (`dnsCurrent`), like a forwarded query, instead of full data currency. The native cache still needs full data currency for its writes: after an ordinary commit an attempt is consumed without writing, as a superseded raw-cache fill already was under D332, and the resolution continues and answers with the same result; the uncached part of the lookup then asks more authority queries (18 to 60 instead of 6 to 13 for a cold validating lookup in the recursor's test world, within the 120-query budget). Anchor retirement, managed-anchor acceptance and the loss of an installed DNS dependency still refuse recursion. | The first part keeps what the unnumbered QUAL-CI review fix (`fix(dns): answer an upstream failure across a canonical commit`) got right: a client whose forwarder failed across a commit gets its SERVFAIL immediately instead of waiting for its own timeout (TestUpstreamFailureAnsweredAcrossCommits, TestCentralQuerylogTwoNodes). That fix decided by status and origin alone, so it also retained refusals the node made itself past a published successor. On a `mode: recursive` node every canonical commit (an API token, any object write) then turned the 60 to 90 ms until the next publication into immediate SERVFAILs with extended error 23 for cache-miss lookups that no authority ever saw; before it, those lookups got no answer and succeeded on the client's retry. The cause was that native recursion demanded full data currency at its start, although its answer is retained under D332 like a forwarded one; recursion on the retained lease removes that window, and the answers stay correct because no write of the retired generation reaches the shared cache. Reproduced before the change by TestRecursiveAnsweredAcrossCommits (`commit 1 of 5, query 21: SERVFAIL EDE 23 ... stand-in root asked: false`). | Narrowing the release alone (a recursive node would still drop every cache-miss lookup in that window and depend on client retries); releasing by status and origin (node-produced refusals presented as network errors); deciding by wire shape or extended error code (provenance must come from the pipeline); failing the resolution when a native cache attempt is superseded (the cause of the window); letting superseded native writes into the cache (breaks D313/D332 data currency); capturing a successor publication or retrying the query (renews a lifetime, rejected by D332) |
