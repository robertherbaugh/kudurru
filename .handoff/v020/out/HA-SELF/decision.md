# HA-SELF decision row (complete corrected D368)

This replaces the D368 row in out/HA-AUTH-SETTINGS/decision.md. The forwarded-domain sentence, the new `auth.password`/`auth.tokens` sentences, the reasons and the rejected alternatives changed.

| D368 | The v0.2 follower contract: forwarded domains, local commands and one typed refusal | Every API operation with an unsafe method has one follower class, kept by operation ID in one table (`internal/api/follower.go`) and published as `x-kudurru-follower`. `forwarded`: the follower sends one typed member command and relays the primary's answer. The forwarded domains of v0.2 are the blocking switch (D357), canonical object writes and the four zone convenience commands (D362), local password login (D363), sign-out with own-session revocation (`auth.logout`: `POST /auth/logout`, `POST /auth/logout/browser`, `DELETE /auth/sessions/{id}`), the cluster settings patch (`settings.patch`: `PATCH /settings`), the caller's own password change (`auth.password`: `POST /auth/password`) and personal API tokens (`auth.tokens`: `POST /auth/tokens`, `DELETE /auth/tokens/{id}`). The allow/deny domain commands and unblock decisions stay `primary` in v0.2: the same list edit is forwarded as a BlockList object write. Both new commands follow D362/D363: the follower bounds the route to 30 seconds before body read, admits the credential against its leased view, captures its source once and sends one version-2 command with the raw credential proof; the primary verifies that credential again in the member transaction, where effect, audit and dedup commit together; clean refusals are retained results; an unsent command answers `503 unavailable`, a failed exchange `503 completion_unknown`; nothing is retried. `auth.logout` revokes the session that the primary itself derives from the verified cookie (`AuthenticateCurrentSessionWithClock`), never a claimed one; a token or JWT caller revokes nothing; `DELETE /auth/sessions/{id}` keeps the route's owner check and a retained `404`; a credential the primary no longer accepts is a retained `401`, except that a command whose dedup record exists is aborted so that a revoked credential never recovers its own retained outcome; the result is emitted under the command scope only (no credential lifetime), because the command may revoke its own credential; no audit row is added, as on the primary's own route. On the follower a sign-out always clears the browser's cookies, also when it was not sent or its outcome is unknown, and then says that the session may stay valid until it expires; a successful one pulls once so that the follower refuses the session at once; a follower offers no provider logout continuation. `settings.patch` carries the merge patch, the If-Match and an unstored random nonce, with the resourceVersion of `Kudurru/default` in the follower's view as precondition (a stale one is a retained `409 conflict`); the primary runs `ForwardedSettingsCommand`, which repeats the route's key, scope, lock and value checks, merges into the transaction's singleton, checks branding against the transaction's pinned license (`deps.License`, again at commit) and stages one write whose object audit row carries the original caller; refusals before the write (`400`, `402`, `409`, `412`) are retained and a failed write rolls back; the follower pulls once and answers with the primary's body under its own node name when its published view no longer carries the precondition version (at most five seconds; a failed pull or late publication still answers the commit), so that the caller's next change or blocking switch through it is not refused as stale, and the settings schema no longer marks cluster keys read-only on a follower. `PATCH /node/config` stays `primary`. `auth.password` carries the current password, the factor code, the hash of the new password (the follower checks the length rules and hashes it; the plaintext never travels), `revokeTokens`, the client key, for a cookie caller a follower-prepared session ID and CSRF hash, and an unstored nonce; the primary verifies the raw credential and runs `ChangeForwardedLocalPasswordWithAdmission`, its own route's admission (shared counters, current password, factor, account manager) that enrolls exactly the prepared session; credential refusals, lockouts (`429` with its Retry-After) and `managed_by` are retained results whose counters commit; the result is emitted under the command scope only; after the commit the follower pulls once and seals the new cookie, or for a token caller answers from the first view that carries the new hash (at most five seconds) and otherwise from the latest view for the original account with `mustChangePassword` false, as the primary's own route answers from the postcommit account; a cookie caller whose session cannot be sealed within the route's bound gets `503 committed_output_unavailable`, so a committed change is never answered `unavailable`, which means that nothing was sent; the two LocalUser object audit rows of the shared password body, and the one APIToken row of a token creation or revocation, carry the original caller in the member commit. `auth.tokens` runs the routes' own bodies (`stageToken`, `deleteTokenCurrent`): for a creation the follower generates the token and sends only its ID and secret hash, because a retained outcome may not be sensitive, and the primary checks the staged row against that hash (`AuthenticateIssuedTokenCurrent`); clean refusals before the write are retained; a revocation keeps the owner-or-`tokens.delete` rule and its retained `404` and is emitted under the command scope only, because it may revoke its own token; the follower answers once its view authenticates the new token or no longer lists the revoked one (at most five seconds). For both, a credential that the primary no longer accepts or authorizes is a retained `401` or `403`, with the dedup guard of `auth.logout`. `kudurru login --username` therefore works against a follower and sends no role preflight. `local`: the node's own response cache, query log, resolver and DHCP server, the cluster commands that decide from the node's own role (promotion runs on a follower; activation and invitations keep their `409`), and the two legacy settings-ownership routes that refuse on every SQLite node. `primary`: everything else, and every operation that the table does not name, including the two import previews, which write nothing but plan an apply that only the primary runs (the decommission preview's revision is the primary's resourceVersion that the decommission checks). A `primary` operation is refused on a follower by a route middleware attached where routes are declared, after authentication and the permission check and before the body is read: `503 primary_required`, with the primary's name, a hint and no `Retry-After`. The role is that of the request's own source (the authority its lease captured before authentication), never a later sample. The writer seams (`currentAuthCommandThen`, `currentAuthCommandOutput`, `MigrationCommand`) and the provider-login admission answer the same key when a follower's request reaches them without passing the router. `GET /cluster` reports `role`, `primary`, `primaryRequired` and the operation IDs of the forwarded and local classes; the settings schema marks a key read-only when its PATCH would be refused; a follower's `GET /auth/status` carries `role` and `primary` and lists no OIDC provider; the follower's block page replaces the unblock form with a message. `POST /cache/flush` runs on a follower without a transaction, authorized against the request's leased authentication view. A fenced or conflicted member, whose API is closed, answers `503 cluster_fenced` or `503 cluster_conflict` with a hint and no `Retry-After`, from the lease adapter (after its bounded capture wait) and from the provider-login admission alike; `generation_pending` with `Retry-After` remains for a publication that is being prepared. | A follower answered every unforwarded mutation with the generic `503 unavailable`, "current writable serving generation unavailable", the same text as a transient publication gap, and a list refresh answered `202` although nothing fetches on a follower. V2-HA requires that read-only and fenced status and forwarding failures are explicit. D362 rejected a generic reverse proxy and forwarding without typed domains, and D300 is the precedent for a typed refusal that UI capabilities reflect. A default at the route-declaration layer cannot be missed by a route added later: it is refused until a reviewed line classifies it, an inventory test fails for a registered mutation without a line, and a mounted follower test requests every registered mutation. The role comes from the request's lease because the original-source rule forbids deciding from a replacement source. Dropping `Retry-After` keeps clients from retrying a state that only an operator, a promotion or the next pull ends. Sign-out is forwarded rather than refused because D363 lets a follower create sessions, and a session that cannot be ended where it was created is a correctness defect; settings is one route with a transaction-level plan seam and the first domain the tracker names. Self-service password and tokens are forwarded because D363 lets a must-change user sign in on a follower, where every other route then answers `403 password_change_required`, and `kudurru login --username` against a follower left a session it could not use. The allow/deny domain commands do not take the D362 pattern cleanly: their eleven routes build closure plans inside the transaction instead of a re-entrant command body over decoded input, `POST /queries/{id}/actions` resolves its domain from the answering node's own query log and the source-entry patch edits list bodies; unblock decisions write their decision audit row through the API layer outside the command's transaction (`recordAction`) and flush the answering node's response cache, so a forward would split the effect from its audit row. | A generic HTTP proxy to the primary (rejected in D362); per-route edits or a refusal only at the writer seams (a route that never opens a writer transaction, such as list refresh, is missed, and a new route is forwarded or refused by accident); a refusal in the HTTP middleware before route matching (answers before the permission check and for paths that are no routes); `409 conflict` or `421` (every mutating operation already documents `503`, and `read_only` is the precedent); a capability by RBAC resource and verb (`blocklists.write` covers both a forwarded editor route and the refused allow/deny commands); reporting `fenced` on `GET /cluster` (a fenced or conflicted member serves no API request, so the field could never be true); forwarding node log settings (the primary's row is not the follower's) or forwarding a cache flush (it would flush the wrong node); keeping `generation_pending` with `Retry-After: 1` for a durable conflict; refusing sign-out on a follower and clearing only the cookie (the durable session would survive); refusing self-service password and tokens on a follower (a must-change user signed in there has no way forward); forwarding the token secret or the new password (a retained outcome may not be sensitive; the dedup fingerprint must be no oracle); hashing the new password on the primary (the plaintext would travel and the primary would spend the hash under its writer lock); aborting the exchange for a clean token or password refusal (reports `completion_unknown` for a known answer); forwarding the allow/deny domain commands and unblock decisions in v0.2 (closure plans, node-local inputs and an audit row outside the transaction need typed re-entries first); revoking a session ID that the follower names for a sign-out (the primary derives it from the verified cookie); aborting the exchange for a credential the primary no longer accepts (reports `completion_unknown` for a clean answer); merging a forwarded settings patch into the primary's current settings without a precondition (could overwrite values the caller never saw) or forwarding the follower's merged values (stale map leaves); an extra `settings.write` row in the primary's chain (the object audit row in the same commit already attributes the change); reading the Store's current authority to decide a request that already holds a lease; classifying the import previews as `local` (their plan would come from a replica that may lag the primary that applies it) |
