| D406 | Follower forwards across a same-source publication | An enrolled follower's forwarded command that passes `withMemberForward` (an object write or delete, alone or as an item of `POST /apply` or `:batchDelete`, a zone convenience command, the blocking toggle and the settings patch) checks before it sends and again before it relays that the follower still serves the source the request captured, not that the request's publication is still the one served (`Publisher.CheckSourceLease` instead of `CheckReadLease`): the Store's authority, including its installed revision, must still be the lease's own, the lease's dependency cursors must still be current, and the host, keyring, provider-resource and runtime checks stay as they were. A later publication of the same installed image therefore no longer cuts the request; an install (a pull), a fence, a term change or a dependency change still cuts it exactly as before (D375, D368). Reads and local commands keep `CheckReadLease`. The two D405 changes stay. | Since D405 a `Wake` that arrives while a preparation runs is answered by one more preparation after the first one publishes, instead of canceling it. On a follower with managed root anchors the anchor source wakes the publisher during every pull's own preparation, so every install was published twice, the second time with the same generation 0.2 to 1.4 s later (measured with an instrumented build: 25 such pairs on one follower during one test; with static anchors the second publication even had the identical dependency identity). The request lease of a forwarded apply captured on the first publication was refused at the next item (`serving: generation pending`, answered "the enrolled primary is unavailable; the write was not applied"): every enrolled-cluster e2e test failed at document 2 to 6 of 200 in hosted CI and locally. What the follower reads from its publication (the auth view of its early admission, the stored object that names the scope) comes from the source, which is unchanged, and the primary reauthorizes the original credential against its own stored object in its own transaction, so the exact publication pointer protected nothing that the source and dependency checks do not. | Bringing back the Wake cancellation (the starvation D405 measured: two preparations per commit, a steadily committing node not publishing); skipping a Wake's publication when its identity equals the served one (managed anchors change the identity on every preparation, so it does not help there, and some tests and callers use a Wake to force a publication); recapturing a newer lease for later items (D375 binds every item to the captured source; same result with more surface); waiting for the second publication before a forwarded request starts (a race, not a rule) |
