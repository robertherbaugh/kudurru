| D383 | Why the three remaining live dnsdist tests failed, and where each fix belongs | (5) None of the three failures was an edge or dnsdist fault. The product behavior they ran into is not changed for v0.2.0; that is a release-acceptance call for the owner, with the measured window below and the follow-up row. Each failure came from a one-shot DNS query sent while the backend was still committing work the test had just caused. A zone write lands as several commits (status, zone lifecycle source, primary head), spread over 1 to 5 s under race instrumentation on a loaded machine. Until the lifecycle admits the new source, the changed zone gets fail-closed coverage, so the forward zone answered SERVFAIL. An authoritative answer captured from a publication that a later commit supersedes is withheld by design (D313, D332), so the query gets no response at all. Measured once without `-race` and with `CGO_ENABLED=0` (a mounted `runServe` test binary, not the packaged release binary; 8 shared CPUs at load 11 to 18; a direct UDP probe every 10 ms per zone; 8 rounds of 7 writes, 4 s apart; QUAL-OPEN3 `fix-measure03-release.log`): any canonical commit, including an unrelated BlockList create or delete, left an authoritative zone unanswered (no response) for up to 586 ms. A write to that zone or its records gave SERVFAIL then no response, up to 860 ms in a row. A forward zone gave SERVFAIL up to 558 ms after its own write and was not affected by other writes. With no writes, no probe failed. The fix is in the harness: `writePublished` waits for the settled source and a quiet installed publication after each mutation, not only before it. The anchor edge test waits for its backend's startup commits and a direct authoritative answer after each backend start. The internal rate limit (20 requests per second per address, burst 40), the 25 s waits and the 500 ms quiet window are unchanged. The F39b 429s came from the harness's 100 ms zone poll plus its observer. The production default `--zone-poll` is 5 s, 0.2 requests per second per edge, so one address would need about 100 edges behind it to reach the limit. | Diagnostic runs at `de8d3cdb` measured each failure on real seams: a UDP relay between dnsdist and the node, a read-only commit watcher on the node's SQLite store, and dnsdist and supervisor counters. The edge forwarded every lost query (backend `queries` and `downstream-timeouts` both rose by one), and the node received it and never replied. Every loss came within about 1.3 s after a commit, before the next publication was installed. The forward-zone SERVFAIL came from the node itself (direct query rcode 2 at publication 22, rcode 0 at 23). The likely reason the same tests passed in the November 2-8 runs is timing: the reconcile then finished before the next one-shot query. That is not demonstrated; no retained run compares reconcile timing then and now. | Retrying the DNS assertions (the tests assert edge behavior on a settled backend; neither retries nor the chosen settle waits bound the window, which the follow-up row tracks, including a bounding test); a longer quiet window only (a zone reconcile can pause for more than 500 ms between commits, which diag06 showed); raising the internal rate limit or lengthening the 25 s deadline (neither caused the failures); emitting stale authoritative data or a SERVFAIL substitute for a withheld answer in v0.2.0 (changes D313/D332 late in the release, and an immediate SERVFAIL is still a failed answer for the client; drafted as a follow-up instead) |
