| D373 | Upgrade failures: what verification left open (amendment) | (1) On SQLite the record set's own conditions report each endpoint the committed primary leaves out for dynamic ownership: the committed primary status (`PrimaryStatus.DynamicOwnership`, from `PreparedImage.CommittedDynamicOwnership`) indexes the dynamic records of the committed head, the leader controller checks the kept endpoints of every record set of a primary zone against that index on each zone reconcile with the same `DynamicOwnership.Conflicts` the compiler uses, and reports each collision as a `Duplicated` conflict (Degraded while something is served, not Ready when nothing is); record sets whose conflicts change are re-queued, and an unreadable head keeps what was reported. The Kubernetes path is unchanged. (2) `DynamicOwnership` is an index by name (dynamic DNAME owners, and every name at or above a dynamic record), so a check costs a few lookups per label instead of a scan. (3) The first operational reload after a complete-serving start, which applies `Kudurru/default` over the file's cluster keys, logs instead of `settings applied`: for the hot keys it just reconfigured, a warning naming them with the stored values now in effect (scalar values only; list and object values such as `rbac.bindings`, `auth.identityProviders`, `querylog.sinks` and `upstreams.groups` are left to `kudurru settings get`); for the restart-required keys, which it does not reconfigure, a second warning naming them and saying the process keeps the values it started with, with no value claimed, because components such as the block page and list loading are built from the startup configuration. Later reloads log `settings applied`. (4) The awaited-body wiring test proves the wake by attribution (no identity provider in its fixture; it fails if a store generation, authority or provider change fired before the list blocked), not by a deadline. (5) The ownership index carries the version of the committed head it was built from; the controller keeps a zone's dynamic conflicts when both its zone view (cached per zone version) and that nonzero head version are unchanged, because every publication re-queues every primary zone. | The record set is where operators look, and the compiler and the controller must agree on what a collision is, so both use one index read from committed data rather than a second rule. A first pass that says "settings applied" for values the file does not hold reads as the opposite of what happened, and naming the stored value of a restart-required key as in effect would be the same mistake the other way round. A deadline race between the wake and the identity provider's ten-second discovery retry let the test pass without the wiring in 3 of 12 runs. | Extending the committed source envelope with per-endpoint reports (a committed-format change late in the release, and the envelope holds no endpoint indexes); a reason string on a `served` projection (parsed back by the controller); scanning only when the zone is small (keeps the quadratic worst case); suppressing the first-pass log entirely (hides why the file edit had no effect); naming a per-key effective value for restart-required keys (which value each component took at startup differs by component and is not known to the reload); logging whole list values (identity and endpoint configuration in the node log where neighbors log names); caching the index on the prepared image (each publication prepares a new image, so it saves nothing on the per-publication path); a 2 to 3 s deadline (still a race, just a narrower one). |
