| D401 | UniFi optional writes: mirrored DNS policies, DHCP DNS servers and client block | Each UniFi write is off by default, enabled per Integration, and runs only as an explicit operator command on SQLite (the Kubernetes root refuses an Integration that enables one with `UniFiPushUnsupportedOnKubernetes`). `push.mirrorRecords` (now with `domains`, required when enabled, `labels` and `exclude`) makes the UniFi provider a publisher of A and CNAME records into the site's DNS policies through the ordinary plan, ledger, intent and receipt path; its roles carry the new `Reviewed` flag, so a poll or reconcile tick builds and applies no plan and only settles a pending intent from a fresh complete reread, while new operations run only from a reviewed sync bound to a preview digest. A DNS policy has no field for a marker, so the adapter reports A/CNAME policies as `Unmarked` rows (a new omit-empty `plan.RemoteOwner` field that leaves every marked provider's digests unchanged) and every other policy as a claim on its name; the planner treats an unmarked row as the owner's exactly when the confirmed ledger of its RRset lists its ID, recovery also accepts an ID acknowledged to the intent's own receipt, and any other policy is a conflict that is never modified or adopted. An unacknowledged write records no ambiguous fact: the intent stays pending, a policy it may have made is never owned, and the next poll abandons the intent without a write only when the site shows exactly the baseline. A create cut off after some of its policies were acknowledged is abandoned the same way once none of the acknowledged policy IDs exist any more (the ledger takes them as `Observation.Gone` and keeps the facts as `undone`); only a publisher without a recovery path gets this exit. `push.dhcpDNSServers` (with new `dnsServers`, one to four IPv4 addresses, and `networks`) advertises the `dhcp-dns-servers` action: `mode: preview` returns per-network `update`/`unchanged`/`missing`/`unsupported` with a digest that binds every network body read, and `mode: apply` with that digest sends one PUT per changed network (the body as read, without `id` and `metadata`, with only the IPv4 DHCP DNS server override replaced) and rereads to confirm. `push.clientActions` (requires `legacy: true`) advertises `block-client` and `unblock-client`, one legacy `cmd/stamgr` command each. All actions need `integrations.act`; an acknowledged action returns its answer in the new `result` field, the act audit row names the action and the SHA-256 of its canonical parameters, an action may refuse before any effect only with a stale review (`409`) or an inapplicable plan (`501`), and every other failure is `integration_uncertain` with no replay. | The design record (§9.5) asks for these three writes, disabled by default, and D291 binds every effect to one reviewed, audited, single-attempt operation. The record mirror is a record sink, so reusing the planner, ledger and receipts gives it previews, digests, drift, idempotence, recovery and `Delete` cleanup without a second engine; only automatic publication had to go, because a gateway's resolver is the operator's and a background reconcile would write it unreviewed. Without a marker, ledger-recorded IDs are the only ownership proof that a copied or hand-made policy cannot forge. The DHCP override and station commands are not RRsets, so they are actions; binding the DHCP digest to the full bodies read makes any concurrent edit of those networks refuse the apply. Kubernetes has no audit table for act and no UniFi publisher in v0.2. Proven against a TLS double of the documented Network API only; no live controller was exercised. | Automatic periodic mirroring like Cloudflare; adopting or overwriting existing policies at a selected name; an ownership marker smuggled into the domain or a disabled sibling policy; replaying or resuming an unacknowledged create from a poll; modeling the DHCP override as a synthetic RRset destination; a separate preview route for DHCP; restoring previous DHCP servers automatically; client actions on the official API's guest-authorization endpoint; running UniFi writes on Kubernetes; importing a third-party UniFi client |
