| D367 | Integration `deletionPolicy: Delete` cleanup lifecycle | An Integration whose policy is `Delete` carries the reserved finalizer `kudurru.io/integration-cleanup`, so every delete path (a removed file document, `kubectl delete`) leaves a readable terminating object with its spec, credential references, UID and status; no tombstone kind or delete API is added. SQLite admission arms the finalizer in the same write as the spec, and no manager's apply, `Force` included, can set or strip it. A live `Delete` object that is stored without it is paused (`CleanupFinalizerMissing`), and the SQLite root refuses every effect of such an instance inside its transaction, so nothing is owned unarmed. Kubernetes has no kudurru admission: once a host runs there (DEL-8; none does in v0.2), the elected host is to arm it with an exact-resourceVersion metadata patch before any ledger intent, and the driver carries it through `Force` takeovers. Each job holds one mode (normal, cleanup, release), derived from the captured object and re-checked by root against the object read at every effect; a change of mode cancels and joins the job before its successor is elected on the same per-instance key. The cleanup job repeats bounded runs on fresh frames, each taking a concurrency slot only while it runs. A run resolves pending intents from a complete reread and then deletes, through the unchanged intent, fence, budgeted request, receipt and confirm path, only record sets whose rows all carry this cluster and UID marker, whose provider IDs are all in the confirmed ledger baseline, and whose name has no conflict. For those, `Delete` overrides per-zone and ledger-retained `upsert-only` and `create-only`. A partially applied delete is resumed in cleanup even after the credential or configuration changed; any other partially applied intent stays pending, because nothing is desired any more. A ledger row is forgotten by exact UID and version only when it has no pending operation and its record is absent (a confirmed delete, or a fresh complete observation that holds none of its provider IDs and no marked row at its key). Then one fenced transaction purges the local state of the instance's source (source-owned record sets and zones, source head and chunks, name allocations, deliveries, inventory clients) and, once the published state shows none of it, another verifies that nothing of the incarnation remains, removes the finalizer by exact UID and resourceVersion and writes an audit summary (on Kubernetes, with DEL-8, sequential exact-identity deletes). Operation history, which nothing prunes while an instance lives, is never held or committed whole: a ledger row leaves with a bounded batch of its operations, and the rest go a stored page at a time once no ledger row is left; a bounded read that meets more than it admits decides nothing and reports `CapacityExceeded`. Proven record sets are deleted even while others block, but nothing is finalized while a conflict, a marker without ledger evidence, ledger provider IDs that still exist without the marker, rows of a destination no longer in the spec, an uncertain receipt or leftover local state remains; each is reported with a specific reason and counts and re-evaluated at the resync interval, at most every ten minutes. Suspension and an expired license pause the cleanup without provider I/O; a missing credential pauses only the cleanup of a publisher, since an inbound instance owns nothing at its provider and its cleanup makes no provider call. A terminating object that carries the finalizer under any other policy is released: SQLite admission does so in the apply that changes the policy, and the host's release job, which needs no license, credential or provider, does so for state no apply stored. The shared request budget row is never deleted. | `Delete` was refused (D239) because treating it as `Retain` silently breaks the operator's promise, and `Retain` leaves records that a recreated Integration, which has a new UID, can never adopt. A finalizer is the one durable tombstone both stores already honor; it keeps the credential reference (D197) and a status surface on the public object and covers the only SQLite delete path. A marker can be copied with a record and a ledger row can outlive a record someone took over, so both must agree before anything is deleted (D206). Budgets and fences must survive rotation and failover (D209), and deletes bind original identity (D291, D302). A complete image may never hold a source head without its chunks or allocation evidence without its allocation, which makes the local purge one transaction. An operator must always be able to end a terminating object without the provider, the credential or the license. | A private tombstone kind (a second copy of credential references, no public status, diverging drivers); synchronous cleanup inside one reviewed delete command (misses file removal and `kubectl delete`, cannot fit large zones in the operation bound); deleting on marker alone or on ledger evidence alone; honoring `upsert-only` or `create-only` during cleanup; finishing a partially applied create or update only to delete it; finalizing partially or over an unresolved receipt; deleting nothing until every record set is provable (a late conflict would undo it anyway); requiring a credential and a reachable controller to purge local state; holding a concurrency slot while blocked; arming in the Kubernetes driver's Apply, which nothing clears while no host runs there; deleting or resetting the request budget; keeping the refusal |
