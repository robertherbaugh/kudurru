# Complete D375 row (HA-OPEN7)

This replaces the D375 row of `out/HA-OPEN5/decision-D375.md` as a whole. A forwarded request now holds the follower's scheduled pull, so the follower's own pull no longer cuts a large apply; the cut item's message no longer says that running the file again stops the same way.

| D375 | Multi-item requests through an enrolled follower | A follower bounds one 30-second lifetime, before body read, for every route whose effect it forwards as `objects.write`, `objects.delete` or `zones.command`: the `/objects` routes, `POST /apply`, the `/blocklists`, `/clientgroups` and `/policies` routes, `POST /{kind}:batchDelete` and the four zone convenience commands (25 registered routes, named by one predicate; a test observes which registered routes reach the forward hooks and holds the predicate to them). Every other `POST`, `PUT` and `DELETE` under `/objects/` and `/zones/` keeps the same bound on a follower, as it had before the predicate (`POST /zones/{zone}/notify` is the only registered one; it is not forwarded). `POST /apply` and `:batchDelete` send one member command for each document or name, in order, inside that single lifetime and keep their ordinary `200` answer with one result for each item. An item is reported with `unavailable` and its cause, is not applied and is never replayed when the lifetime has ended, when the request was canceled, or when the follower's own installed source changed since the request began. A forwarded request holds the follower's scheduled pull from before it captures its source until it ends (`holdMemberPulls`, `Coordinator.HoldPulls`, HA-OPEN7): a pull that is installing when the request arrives is waited for first (at most five seconds), so the request is bound to the installed source, and the scheduled pull then waits for every holder, at most `MaxPullHold` (the 30-second request lifetime), and installs anyway after that. Explicit pulls (after a forwarded sign-in, sign-out or settings change) do not wait. The follower applies nothing itself and no item is retried or replayed; the hold only delays the next install. So a request is cut only by such an explicit pull, by the scheduled pull after 30 seconds, or by its lifetime: one apply of 200 documents through a follower applies all of them (process test). That last refusal of an item says what to do: "the follower's source changed while this request ran (...); this item was not sent and was not applied, and neither was any later one; send the items that were not applied, or the whole file, to the enrolled primary <name>, which applies them in one request" (`memberItemRefusal`, for contexts that `api.InObjectItems` marks). A request that began on a follower stays a forward after its context has ended: `ObjectForward` and `ZoneForward` read the mode of the request's original lease (`servinghttp.SourceMode`, which returns no token) and answer that refusal themselves instead of falling through to the node's local command. An item whose exchange with the primary fails keeps the answer of a single forwarded write, `completion_unknown`; so does an item, or a single forwarded write, whose answer the primary sent but which the follower could not relay because its own source or membership changed during the exchange (before: `unavailable` "cluster authority changed", which said that nothing was made). In a multi-item request that answer adds that the later items were not applied and names the primary. Earlier items stay committed. There is no document cap and no new status. A capture refusal names its cause (source changed, lifetime ended, canceled, route not forwarded) instead of always reporting a changed source. | D362 already claimed `kudurru apply` and the dashboard editors, but only `/objects/` and `/zones/` paths were bounded, so capture refused every other route and reported a changed source. Apply and batch deletion already define per-item results on every node. The primary lets a request follow its own commits by an exact compare of command receipts (D378). Chaining a follower's later items in the same way was examined again (HA-OPEN5) and does not hold with the present protocol. On the primary the chain compares the provider coordinator's mark of the last state-changing command by identity, in process; a follower would need that mark as a serializable receipt in every member outcome, a new command field that the primary checks against its current mark before admission, and a rule under which the follower accepts a newer installed image, and a newer lease for its own pins and credential view, for a request that began on an older one, because its admission and the dependency pins of every forward are bound to the request's own publication (`CheckReadLease`). That is a member protocol change on both sides and a second admission rule for followers, not a fix, and this lane does not carry the D378 coordinator code of the release branch it would build on. So the original-source rule (capture once, never retarget) still forbids continuing a request across a source change on a follower. What changed the source was almost always the follower's own scheduled pull of the request's earlier items: HA-OPEN6 measured a 40-document file applied completely 5 of 18 times and a 160-document file never, and in one hosted run 84 of 200 new documents were refused. Holding that pull while the request runs keeps the source the request captured without retargeting anything, deciding anything on the follower or replaying an item (HA-OPEN7: the mounted test with 100 ms pulls was cut at document 4 without the hold and passed with it; the process test applies 200 record sets). The earlier objection to deferring pulls (it holds replication, and fencing with it, and requests can follow each other) is answered by the bound: each scheduled pull waits at most 30 seconds, then runs while new holds wait for it, so replication runs at least once per interval plus 30 seconds even under a stream of requests, and fencing stays decided by the primary's term checks on every forwarded command (a follower that learns a new term later still has its forwards refused by a fenced old primary or by the new one). Reads on the follower can lag by up to that bound during forwarded writes. A partial result stays the honest outcome when the source changes anyway. Skipping documents that the follower's own view shows unchanged would answer a write from the follower's data, including when a document repeats a key that an earlier item of the same file changed on the primary, and committing no deduplication record for an unchanged result would remove the guard against a late replay of the same command; both were rejected. Such a file goes to the primary, which applies every document in one request. Before the review fix an ended request fell through to the local command, whose credential check answered `401 unauthenticated`, "current credential is invalid or expired", for a write that had only run out of time. | A typed `413` document cap for follower requests (an arbitrary number that would refuse applies that fit, and that would not remove the source-change cut); a longer or per-item lifetime (extends the original request bound); re-capturing a new source for later items or retrying a refused item (retargets or replays a decision); making apply atomic across documents on a follower (it is not atomic on the primary either); chaining a follower's later items on the primary's receipts as D378 does on the primary (needs a serializable chain receipt in the member protocol, a primary-side check of it and a follower rule for accepting a newer image and lease mid-request; recorded for a later release); an unbounded pull hold (a stream of requests would stop replication); holding explicit pulls too (a forwarded sign-in or settings change inside a held request would wait for itself); taking the hold after the request captured its source (a pull installing at that moment still cuts the request at its first item); answering `unchanged` on the follower from its own view (a write decided from the follower's data, wrong for a key repeated in the file); no deduplication record for an `unchanged` result (removes the replay guard); a blanket 30-second bound for every unsafe follower request (would cut node-local work such as lease import or query-log purge); bounding only the forwarded routes (takes an existing deadline away from the other unsafe requests under `/objects/` and `/zones/` for no gain); letting `SourceToken` answer for an ended context (hands a comparison token to a request that may no longer act); deciding the role from the Store's current authority instead of the request's lease (samples a replacement source) |
