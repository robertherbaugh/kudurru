| D381 | RFC 2136 UPDATE from enrolled SQLite followers | An enrolled SQLite follower that is not the ready writer selects the zone in its own complete cut (NOTAUTH otherwise), uses the listener's verified TSIG proof and admits the key against its own current keyring (REFUSED for a missing proof or an unknown key). When its source changed under the request before anything was sent (it installed a newer commit, in a burst usually the previous update's own, or replaced a dependency, so the keyring is no longer current or the forward capture refuses the changed source), it waits, inside the forward's four-second bound, for its own current complete publication (`awaitFollowerPublication`), selects the zone and admits the key again there and captures the forward on that source. The same wait follows a source change that the forward finds only when it acquires the store for the exchange, before the exchange with the primary began (`EnrolledForwarder.Forward` joins `clusterreplica.ErrNotSent` to every error returned before the member client is called); the same command ID is then sent once. A command is sent at most once, and a refusal after the exchange may have begun is never followed by a second send. It then sends one version-1 `dns.update` member command: the exact request without its TSIG record, a `TSIGKey`/`tsig` subject naming the key and its secret-derived credential version, the algorithm, transport and signature deadline, bounded by four seconds, the DNS request and the signature. The primary runs the command on its current writer publication (`runMemberUpdate`): it waits for one within the command's bound (`Publisher.WaitTerm`) and captures it, admits the exact key identity (name, algorithm, credential version) in its own current keyring, then runs the native protocol adapter under its elected writer, so zone selection, grants, prerequisites, atomic commit and publication are identical. It runs the same command ID again, after the next publication, only when its SERVFAIL decided nothing that the command ID does not already retain (`memberUpdateRerun`): when `captureUpdate` rejected it only because its lease was no longer the current writer publication, its keyring stopped being current or the publication did not admit or route the zone at that moment (`forwardedUpdate.stale`, set before admission), when every compare-and-swap attempt of `Apply` lost against another writer of the zone and nothing committed (`pr.ErrConflict`, seen through `network.WithOutcome`), or when `Apply` decided it and only the zone's publication failed (`UpdateOutcome.PublishFailed`: the publication of its own commit, of a retained outcome the receipt ledger returned, or the recovery publication of an earlier commit; HA-OPEN7). Once an attempt committed, the next run finds its receipt and answers the retained NOERROR, and only that answer may follow (`memberUpdateRetained`); any other later answer (a key or grant changed since, a zone that began retiring) becomes SERVFAIL. A replayed command ID whose admission refused is final (HA-OPEN6's `replay` condition also reran it). A retiring or retired zone is refused at once, since no later publication admits it; a cause that does not clear ends at the command's bound with SERVFAIL. Every other answer is final. The command ID is the update's retry identity in the zone's receipt ledger throughout, so a repeated delivery or attempt returns the retained rcode without a second commit. The follower derives it from the exact signed request (`memberUpdateCommandID`: SHA-256 over the key name, algorithm and credential version, the transport and the whole message with its TSIG record, so message ID, time signed and MAC are included; HA-OPEN7): a client that got SERVFAIL, outcome unknown, and sends the same signed message again, through this follower or another one, is answered from the retained outcome with the original NOERROR if the first one committed, and a message signed again is a new update decided again. Every forwarded UPDATE answered SERVFAIL is logged at warning level with its stage and cause on the follower and, when the primary decided it, on the primary. The zone runtime commits in its own transaction, fenced by the writer, the term and the admitted key identity; unlike a generic member command, the sender's current enrollment is rechecked in a transaction only when the acknowledgment is admitted, so a member revoked during those milliseconds can still commit and only its answer is withheld (such a member holds the TSIG secrets and could send a native UPDATE). The rcode is acknowledged inside the member request's command output scope (an empty member command after the zone runtime's own commit). The follower relays that rcode, signed with the request's key, under an acknowledgment bound to the verified key and unchanged empty response rather than its own data generation. A command that was not sent within the bound, was refused by member admission, or whose exchange was lost answers SERVFAIL and is never retried by either node; only the client's repeat of the same signed message reaches the same retry identity. Fenced, conflicted, standby and static nodes keep their local SERVFAIL. A native UPDATE sent to the primary is unchanged: right after a commit it can still be answered SERVFAIL before anything is applied. | The v0.2 UPDATE row requires primary routing once follower mode exists. Followers sit behind the same VIPs and DHCP configurations as the primary. DNS has no rcode for "outcome unknown", and RFC 2136 section 4.5 tells the requestor to try its next server on SERVFAIL, which is safe for an unsent update and is the native primary's answer for a committed but unpublished one. The receipt ledger already deduplicates by retry identity, and the zone runtime commits in its own fenced transaction, so the member command adds no second dedup row. Every commit is followed within milliseconds by its publication and by the node's own status and lifecycle writes (a new serial, a realigned lifecycle) and their publications, so a command that arrives right after one meets a publication that is being replaced on the follower, on the primary or both. Answering that with SERVFAIL made a DHCP-like burst through a follower fail: up to 6 of 8 updates in the HA-UPDATE-ROUTING verification, and once the first failed every later one in the burst failed too (30 to 40 ms of consecutive failures). The diagnostic runs of this package found four separate causes: the primary's writer check on a replaced lease (the root burst test fails 4 of 4 without the fix, race08), the follower's keyring check after it installed the previous update's commit (e2e01, e2e03), the primary's zone admission while its lifecycle was being realigned (e2e06), and `Apply` running out of compare-and-swap attempts against those writes (e2e08). None of them decided or committed anything, and both nodes decide again on the newer publication, so waiting for it is the HTTP capture wait applied to UPDATE, not a replay. HA-OPEN6 found a fifth in the same class: the forward capture retains only the token and `WithMemberForward` checks it again at acquisition, so a pull between the two made the follower answer an immediate SERVFAIL (90 to 290 ms) for the third or fourth update of a six-update burst under the production bound in 7 of 7 race runs; a second identical send would have committed. The native UPDATE stays outside D399's recapture because a second capture would admit the same wire message on a second keyring; a forwarded one only re-admits the same key identity (name, algorithm, credential version) on the follower and is decided again by the primary, so its wait is the same pre-dispatch rule as D399. HA-OPEN7: an RFC 2136 client that gets SERVFAIL for an update that was applied sends it again and may then fail its own prerequisite. DNS has no rcode for an unknown outcome, so the follower still answers SERVFAIL when it does not know, and two things bound that: the primary no longer answers SERVFAIL for a cause that only delays the answer of a decided update (a failed publication after the commit, whose next run reads the receipt), and a repeat of the same signed message is answered from the retained outcome instead of being decided again. The mounted test holds the primary's answer past a three-second follower bound, gets SERVFAIL, sends the same bytes again and gets NOERROR for an update whose name-not-in-use prerequisite would answer YXDOMAIN if it ran again; signed again, it answers YXDOMAIN. Including the TSIG time and MAC in the identity keeps a deliberate later update with the same content (a DHCP server adding the record again after a delete) from being taken for a repeat; only a byte-identical message within its signature's time fudge maps to the receipt, and a captured signed UPDATE replayed within that fudge, which TSIG alone does not stop, now changes nothing. | Refusing on followers with REFUSED or NOTAUTH (clients would have to find the SOA MNAME, and REFUSED claims a policy refusal);
