# Complete D375 row (HA-OPEN5)

This replaces the D375 row of `out/CORE-APPLY-MULTI/decision-D375.md` as a
whole. What a follower does is unchanged except for two answers: an item it
cut says what to do and names the primary, and a forwarded write whose answer
arrived but could not be relayed is `completion_unknown`. The "why" and
"alternatives" cells now record why chaining on the primary's receipts was
examined again and rejected for v0.2, and why a repeat cannot finish the file.

| D375 | Multi-item requests through an enrolled follower | A follower bounds one 30-second lifetime, before body read, for every route whose effect it forwards as `objects.write`, `objects.delete` or `zones.command`: the `/objects` routes, `POST /apply`, the `/blocklists`, `/clientgroups` and `/policies` routes, `POST /{kind}:batchDelete` and the four zone convenience commands (25 registered routes, named by one predicate; a test observes which registered routes reach the forward hooks and holds the predicate to them). Every other `POST`, `PUT` and `DELETE` under `/objects/` and `/zones/` keeps the same bound on a follower, as it had before the predicate (`POST /zones/{zone}/notify` is the only registered one; it is not forwarded). `POST /apply` and `:batchDelete` send one member command for each document or name, in order, inside that single lifetime and keep their ordinary `200` answer with one result for each item. An item is reported with `unavailable` and its cause, is not applied and is never replayed when the lifetime has ended, when the request was canceled, or when the follower's own installed source changed since the request began (its next pull, five seconds by default, usually installs the request's earlier items). That last refusal of an item says what to do: "the follower's source changed while this request ran (...); this item was not sent and was not applied, and neither was any later one; send the items that were not applied, or the whole file, to the enrolled primary <name>, which applies them in one request; running it again through this follower stops in the same way" (`memberItemRefusal`, for contexts that `api.InObjectItems` marks). A request that began on a follower stays a forward after its context has ended: `ObjectForward` and `ZoneForward` read the mode of the request's original lease (`servinghttp.SourceMode`, which returns no token) and answer that refusal themselves instead of falling through to the node's local command. An item whose exchange with the primary fails keeps the answer of a single forwarded write, `completion_unknown`; so does an item, or a single forwarded write, whose answer the primary sent but which the follower could not relay because its own source or membership changed during the exchange (before: `unavailable` "cluster authority changed", which said that nothing was made). In a multi-item request that answer adds that the later items were not applied and names the primary. Earlier items stay committed. There is no document cap and no new status. A capture refusal names its cause (source changed, lifetime ended, canceled, route not forwarded) instead of always reporting a changed source. | D362 already claimed `kudurru apply` and the dashboard editors, but only `/objects/` and `/zones/` paths were bounded, so capture refused every other route and reported a changed source. Apply and batch deletion already define per-item results on every node. The primary lets a request follow its own commits by an exact compare of command receipts (D378). Chaining a follower's later items in the same way was examined again (HA-OPEN5) and does not hold with the present protocol. On the primary the chain compares the provider coordinator's mark of the last state-changing command by identity, in process; a follower would need that mark as a serializable receipt in every member outcome, a new command field that the primary checks against its current mark before admission, and a rule under which the follower accepts a newer installed image, and a newer lease for its own pins and credential view, for a request that began on an older one, because its admission and the dependency pins of every forward are bound to the request's own publication (`CheckReadLease`). That is a member protocol change on both sides and a second admission rule for followers, not a fix, and this lane does not carry the D378 coordinator code of the release branch it would build on. So the original-source rule (capture once, never retarget) still forbids continuing a request across a source change on a follower, a partial result is the honest outcome, and the items say exactly what happened and what to do. Running the apply again through the follower does not finish a file that was cut: the follower forwards the committed documents again, the primary commits a deduplication record for every forwarded command, also one whose result is `unchanged`, and the follower's next pull changes its source again; in one hosted run 84 of 200 new documents were refused and four repeats created none. Skipping documents that the follower's own view shows unchanged would answer a write from the follower's data, including when a document repeats a key that an earlier item of the same file changed on the primary, and committing no deduplication record for an unchanged result would remove the guard against a late replay of the same command; both were rejected. Such a file goes to the primary, which applies every document in one request. Before the review fix an ended request fell through to the local command, whose credential check answered `401 unauthenticated`, "current credential is invalid or expired", for a write that had only run out of time. | A typed `413` document cap for follower requests (an arbitrary number that would refuse applies that fit, and that would not remove the source-change cut); a longer or per-item lifetime (extends the original request bound); re-capturing a new source for later items or retrying a refused item (retargets or replays a decision); making apply atomic across documents on a follower (it is not atomic on the primary either); chaining a follower's later items on the primary's receipts as D378 does on the primary (needs a serializable chain receipt in the member protocol, a primary-side check of it and a follower rule for accepting a newer image and lease mid-request; recorded for a later release); deferring the follower's pulls while a multi-item request runs (holds replication, and fencing with it, for up to 30 seconds per request, and requests can follow each other); answering `unchanged` on the follower from its own view (a write decided from the follower's data, wrong for a key repeated in the file); no deduplication record for an `unchanged` result (removes the replay guard); a blanket 30-second bound for every unsafe follower request (would cut node-local work such as lease import or query-log purge); bounding only the forwarded routes (takes an existing deadline away from the other unsafe requests under `/objects/` and `/zones/` for no gain); letting `SourceToken` answer for an ended context (hands a comparison token to a request that may no longer act); deciding the role from the Store's current authority instead of the request's lease (samples a replacement source) |
