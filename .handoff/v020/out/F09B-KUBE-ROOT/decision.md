| D384 | Kubernetes integration root: one source head per Integration UID, per-object ledger CAS, Lease verified before each effect | On Kubernetes the integration host runs on every replica and elects one Lease per Integration. **What is atomic:** (1) a source commit is one create or one exact-resourceVersion update of the `IntegrationSourceHead` of that Integration UID, sequence n to n+1, never retried; the immutable `IntegrationSourceChunk` Secrets and create-only `IntegrationNameAllocation`s it references are staged and rechecked as durable before that write, so a lost head CAS changes no source and leaves only unreferenced chunks; (2) each ledger, operation, budget, delivery and event-cursor write is one create-only or exact-resourceVersion Secret write, never `Force` and never repeated with a fresh version, and only those private kinds can be written or forgotten through the ledger seam; (3) name-allocation exclusivity per scope and label; (4) each Integration status write, by the Lease holder, with the captured resourceVersion as precondition. **What is not atomic, and how it is compensated:** (a) the Lease is a rejection check, not a lock: before each provider request and each store write the root reads the Lease live and refuses unless it still names this replica with the holder, acquire time and transition count recorded when the term started and an unexpired renew time; a request or write already sent after a passing check can still land after the Lease is lost, and is then a serializable predecessor of the successor's CAS or a conflict; the proof assumes one live process per identity, and the identity is the node name, so two live processes that share it (a force-deleted StatefulSet pod still running on a partitioned node and its replacement) both pass it; (b) guard versus write: the Integration's UID, resourceVersion, mode, suspension and spec digest are compared by a live read just before each write, not in the write itself, and a publisher's captured source zones and record sets are compared against the replica's current watch snapshot by UID and identity (everything but status, resourceVersion and managed fields), not by a linearizable read, because the controller writes their status after every change and a resourceVersion compare fenced effects reserved just before such a write; a change that lands between the two is caught by the next fence and by the ledger's pending-intent recovery, which forces a fresh complete reread by any writer; (c) a forget of several ledger rows is a sequence of exact UID and resourceVersion deletes, ledger row first, that stops at the first failure; (d) source-owned DNS children (tranche 2) are separate objects and are not atomic with each other or with the head, which certifies them by UID, resourceVersion and intent digest; (e) inventory and MAC grants are derived on each replica from committed heads (tranche 2) and converge per replica, so "published" means installed on the committing replica; (f) remote provider effects, as on SQLite. **Tranche 1 (this decision's code):** the source backend, the strict carrier decoding, Lease term verification and the root adapter mount Cloudflare publication; only Integrations in the release namespace run, and one in any other namespace is refused with `NamespaceNotAllowed`, because the file and environment credential allowlists are node-wide and an Integration may name any allowlisted credential: allowlisting a credential grants it to every principal who can create Integrations in the release namespace, who can already read kudurru's own Secrets there; UniFi, webhook instances and `deletionPolicy: Delete` are refused with the status reason `UnsupportedOnKubernetes` or `DeletionPolicyUnsupported` before any provider is constructed; a refusal whose status write fails is written again by a new term after the next capture; source selection is unavailable while the controller reports, for an admitted record set's current generation, a `Duplicated`, `Occluded` or `Invalid` condition (the counterpart of SQLite's refusal of a duplicated source projection); unlike SQLite there is no committed primary head to wait for, so a conflict the controller has not reported yet is not seen; native Secret credential references stay disabled (file and environment allowlists only) because the credential namespace is the release namespace, which holds kudurru's own keys; the `/api/v1/integrations` administration routes still answer unavailable on Kubernetes. A lost shared request-budget CAS fails that request (the ledger keeps its single-attempt rule) and the instance retries on its schedule. Supersedes the statements that Kubernetes "cannot use sequential per-object writes" for this root. | Kubernetes has single-object CAS and no multi-object transaction. The source format is already content-addressed chunks plus one head pointer sized for Secret carriers, and the outbound ledger already serializes every effect through one object per record, so one head CAS is a real commit point and the per-object ledger CAS needs no wider transaction. This is not D239's rejected "sequential writes pretending to be atomic": the only multi-object step (chunks before head) is ordered so that every intermediate state is the previous source, and every non-atomic seam above is named with its compensation. Refusing what tranche 1 does not run, with a status reason, replaces the silent no-op of an inert Integration and keeps Delete from silently behaving as Retain. | Strict root-gated serving that hides uncertified source-owned records from every DNS consumer (cross-cutting, exceeds SQLite parity); mounting the SQLite lifecycle runtime on Kubernetes (changes the serving model, D366); sequential per-client writes as the commit (D239); Leases as locks; an automatic budget re-reservation that would weaken the ledger's single-CAS rule; native Secret references in the release namespace without an operator-chosen credential namespace or opt-in label; not advertising integrations on Kubernetes; running Integrations from every namespace with the node-wide credential allowlist; settling every capture on the controller status of each record set's current generation (stops every instance on each record edit until the controller writes status); a per-process nonce in the Lease identity (changes the holder every elector reports; left to K7) |
