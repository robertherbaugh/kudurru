| D367 | Integration `deletionPolicy: Delete` cleanup lifecycle | An Integration whose policy is `Delete` carries the reserved finalizer `kudurru.io/integration-cleanup`, so every delete path (a removed file document, `kubectl delete`) leaves a readable terminating object with its spec, credential references, UID and status; no tombstone kind or delete API is added. SQLite admission arms the finalizer in the same write as the spec, and no manager's apply, `Force` included, can set or strip it. Kubernetes has no kudurru admission: the elected host arms it with an exact-resourceVersion metadata patch before any ledger intent, and the driver carries it through `Force` takeovers. After the normal job is joined, an elected, bounded, resumable cleanup run on the same per-instance key resolves pending intents from a complete reread and then deletes, through the unchanged intent, fence, budgeted request, receipt and confirm path, only record sets whose rows all carry this cluster and UID marker, whose provider IDs are all in the confirmed ledger baseline, and whose name has no conflict. For those, `Delete` overrides per-zone and ledger-retained `upsert-only` and `create-only`. A ledger row is forgotten by exact UID and version only when it has no pending operation and its record is absent (a confirmed delete, or a fresh complete observation that the provider no longer holds it). Local source-owned state is purged and the finalizer removed in fenced transactions with an audit summary (sequential exact-identity deletes on Kubernetes). Conflicts, markers without ledger evidence, rows of a destination no longer in the spec, uncertain receipts, a missing credential, suspension and an expired license block with a specific reason and never finish partially. Changing the terminating object to `Retain` releases it with no provider I/O and is not license-gated. The shared request budget row is never deleted. | `Delete` was refused (D239) because treating it as `Retain` silently breaks the operator's promise, and `Retain` leaves records that a recreated Integration, which has a new UID, can never adopt. A finalizer is the one durable tombstone both stores already honor; it keeps the credential reference (D197) and a status surface on the public object and covers the only SQLite delete path. A marker can be copied with a record, so the ledger must agree before anything is deleted (D206). Budgets and fences must survive rotation and failover (D209), and deletes bind original identity (D291, D302). | A private tombstone kind (a second copy of credential references, no public status, diverging drivers); synchronous cleanup inside one reviewed delete command (misses file removal and `kubectl delete`, cannot fit large zones in the operation bound); deleting on marker alone; honoring `upsert-only` or `create-only` during cleanup; finishing partially or over an unresolved receipt; arming in the Kubernetes driver's Apply, which nothing clears while no host runs there; deleting or resetting the request budget; keeping the refusal |
