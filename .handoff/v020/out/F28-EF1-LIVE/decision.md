| D<nnn> | Managed trust anchors (F28-EF-1): a raced root-anchor update is retried, not terminal | The elected root-anchor updater no longer stops for the whole writer term when an ordinary commit moves the canonical generation under it. Two refusals are non-terminal. (a) The capture refuses with the store's authority CAS (`replication.ErrCAS`) because a commit landed between the image read and the capture; nothing was acquired, and the next step comes one second later. (b) The bootstrap or advance transaction rolls back with `replication.ErrCAS` (definite `AnchorRolledBack`, no denial committed first) because a commit landed while the root reply was in flight. The reply is discarded, never replayed, and a later step makes a new acquisition against the new generation. These retries bind the exact owner, policy and settings identity (the existing retry floor) and are paced at 1, 2, 4 and so on up to 64 seconds while the race repeats. The pace resets on a committed or unchanged update. Each raced step logs a warning with the next attempt time and the consecutive count, so repeated races under write churn are visible to the operator. An accepted-owner change (`accepted.ErrCAS`), an uncertain outcome, a committed denial, a lost term (`ErrFenced`) and every authentication or admission refusal stay terminal as before. A revocation denial that an ordinary commit rolls back (denial rolled back, update unknown) also stays terminal for now: the failed denial closes the anchor source and resolves its withdrawal as failed-or-unknown, which fails closed, and retrying it needs its own design (follow-up). The supported order for a new follower behind managed edges (runbook "Add a follower behind managed edges") is qualified against the pinned dnsdist image with two backends. | The live two-backend run showed the startup zone status write racing the first bootstrap of a fresh managed node: the bootstrap rolled back with "authority changed", and the updater parked for the term. On a standalone node that means no managed trust until a restart, and the restart then acquires the root again. A definite rollback caused only by an unrelated commit changes nothing durable. A new acquisition is a fresh observation, not a replay of a refused or uncertain mutation, so it keeps the no-replay rule. | Keeping every CAS terminal (one zone write at the wrong moment disables RFC 5011 for the term); retrying the same received reply (a replay); an unpaced immediate retry (unbounded root traffic under write churn); using the one-hour minimum refresh as the retry delay (a fresh node would stay without managed trust for an hour) |
