| D<unassigned-1> | Kubernetes answers for forwarded auth and IAM routes without a legacy handler | On the Kubernetes driver the legacy authentication stack serves `GET /iam/rolebindings/{namespace}/{name}` from the cache that backs the list and returns the stored object with its UID and resourceVersion. The public CLI login routes (`GET /auth/cli/providers`, `POST /auth/cli/{idp}/prepare` and `/verify`) answer `503 cli_login_unavailable`, the provider logout continuation routes (`GET /auth/oidc/{idp}/logout` and `/logout/callback`) answer `503 provider_logout_unavailable`, each with a hint, and a last fallback on the legacy mux answers `503 unavailable` ("requires the complete SQLite runtime") for any forwarded route without a handler. `kudurru login` keeps the `cli_login_unavailable` key through its safe-error filter and prints a fixed client message that names `--token` and `--username`. The runtime gate `servingMutationRoutes` on the complete SQLite runtime is removed: every registered unsafe route under `/zones`, `/unblockrequests` and BlockList source entries is a reviewed complete current command, a test holds that table to the registered routes, and an unregistered path gets the router's `404 not_found`. | Six registered routes answered Go's plain-text `404 page not found` on Kubernetes (confirmed by a mounted envtest run), which no client can parse; the gate answered `503 current_command_unavailable` only for paths that are not routes. Public CLI login needs the captured provider resources, receipts and request lanes that only the complete SQLite runtime owns (D286, D287), and server-side session state stays SQLite-only in v0.2 (D54, D364). A keyed refusal uses a status every forwarded operation already declares (503), so no contract regeneration is needed. | Implementing provider advertisement and proof verification on the legacy stack (a new feature on a second code path); answering an empty provider list (the CLI would tell the operator to configure a CLI client this server cannot use); `501` for the fallback (not declared for these operations); `404` for the refusals (reads as a missing provider or object); keeping the gate, or answering `405` from a route-table-aware gate, instead of the router's existing `404` for every unmatched method and path |
| D<unassigned-2> | Multi-item requests through an enrolled follower | A follower bounds one 30-second lifetime, before body read, for every route whose effect it forwards as `objects.write`, `objects.delete` or `zones.command`: the `/objects` routes, `POST /apply`, the `/blocklists`, `/clientgroups` and `/policies` routes, `POST /{kind}:batchDelete` and the four zone convenience commands (25 registered routes, named by one predicate; a test observes which registered routes reach the forward hooks and holds the predicate to them). Every other `POST`, `PUT` and `DELETE` under `/objects/` and `/zones/` keeps the same bound on a follower, as it had before the predicate (`POST /zones/{zone}/notify` is the only registered one; it is not forwarded). `POST /apply` and `:batchDelete` send one member command for each document or name, in order, inside that single lifetime and keep their ordinary `200` answer with one result for each item. An item is reported with `unavailable` and its cause, is not applied and is never replayed when the lifetime has ended, when the request was canceled, or when the follower's own installed source changed since the request began (its next pull, five seconds by default, usually installs the request's earlier items). A request that began on a follower stays a forward after its context has ended: `ObjectForward` and `ZoneForward` read the mode of the request's original lease (`servinghttp.SourceMode`, which returns no token) and answer that refusal themselves instead of falling through to the node's local command. An item whose exchange with the primary fails keeps the answer of a single forwarded write, `completion_unknown`: the member client treats every failed POST exchange, including an unreachable primary, as an unknown outcome. Earlier items stay committed. There is no document cap and no new status. A capture refusal names its cause (source changed, lifetime ended, canceled, route not forwarded) instead of always reporting a changed source. | D362 already claimed `kudurru apply` and the dashboard editors, but only `/objects/` and `/zones/` paths were bounded, so capture refused every other route and reported a changed source. Apply and batch deletion already define per-item results on every node, and the original-source rule (capture once, never retarget) forbids continuing a request across a source change, so a partial result is the honest outcome and the items say exactly what happened; `kudurru apply` is idempotent and can be run again. Before the review fix an ended request fell through to the local command, whose credential check answered `401 unauthenticated`, "current credential is invalid or expired", for a write that had only run out of time. | A typed `413` document cap for follower requests (an arbitrary number that would refuse applies that fit, and that would not remove the source-change cut); a longer or per-item lifetime (extends the original request bound); re-capturing a new source for later items or retrying a refused item (retargets or replays a decision); making apply atomic across documents on a follower (it is not atomic on the primary either); a blanket 30-second bound for every unsafe follower request (would cut node-local work such as lease import or query-log purge); bounding only the forwarded routes (takes an existing deadline away from the other unsafe requests under `/objects/` and `/zones/` for no gain); letting `SourceToken` answer for an ended context (hands a comparison token to a request that may no longer act); deciding the role from the Store's current authority instead of the request's lease (samples a replacement source) |
| D<unassigned-3> | Member command acknowledgment under the commit's own writer exclusion | `Store.MemberCommandWithOutput` runs the acknowledgment of a member command in the command's finalizer: after confirmed SQL completion and before the writer lock is released. Output admission is `WithCommandOutput`'s, unchanged: the exact resulting authority and generation, the original owner, the peer certificate, the deadline and an actual command receipt are all compared again, a refused output is withheld, and completion is reported separately from the output's result. `providercoordinator.WithMemberCommandOutput`, the only production composition (the root's scoped member executor for `blocking.toggle`, `objects.write`, `objects.delete`, `zones.command` and `auth.login`), uses it. `MemberCommand` followed by `WithCommandOutput`, and `ReadImage` followed by `WithOutput`, keep the two-step form and keep refusing after any interposed commit. | The two-step form released the writer lock between the commit and the output. The publication gate excludes other current commands there, but not writers that take only the Store lock, such as status reconciliation. Such a commit in the gap made the exact-authority comparison fail, the member server aborted the response, and the follower reported `completion_unknown` for a write that had committed: the second of two new documents in one of four early two-process scenario runs, and every time in a coordinator test that lets a queued writer run in the gap. D347 already emits a local command's output inside the finalizer under the same lock, and D336 asked for exclusions across the peer transaction and its one response. Nothing that the comparison protects is given up: no acknowledgment leaves for a generation other than the command's own. | Comparing only term, incarnation and membership for a command acknowledgment (an answer could follow another installed generation, and a revocation or authority observation could still land in the gap); re-reading the result or retrying after `ErrCAS` (reports state the command did not produce, or replays a decision); routing every Store writer through the publication gate (a wide change to reconcilers for one window); handing the held lock from `MemberCommand` to a later `WithCommandOutput` call (a caller that never emits would hold the writer forever); keeping the gap and documenting multi-document applies as unreliable (every forwarded write, including a single one, could still report an unknown outcome for a commit on a busy primary) |
