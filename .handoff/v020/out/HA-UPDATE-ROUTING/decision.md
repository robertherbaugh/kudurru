| D381 | RFC 2136 UPDATE from enrolled SQLite followers | An enrolled SQLite follower that is not the ready writer selects the zone in its own complete cut (NOTAUTH otherwise), uses the listener's verified TSIG proof and admits the key against its own current keyring (REFUSED otherwise). It then sends one version-1 `dns.update` member command: the exact request without its TSIG record, a `TSIGKey`/`tsig` subject naming the key and its secret-derived credential version, the algorithm, transport and signature deadline, bounded by four seconds, the DNS request and the signature. The primary admits the exact key identity (name, algorithm, credential version) in its own current keyring, then runs the native protocol adapter under its elected writer, so zone selection, grants, prerequisites, atomic commit and publication are identical. The command ID is the update's retry identity in the zone's receipt ledger, so a repeated delivery of the same command returns the retained rcode without a second commit. The zone runtime commits in its own transaction, fenced by the writer, the term and the admitted key identity; unlike a generic member command, the sender's current enrollment is rechecked in a transaction only when the acknowledgment is admitted, so a member revoked during those milliseconds can still commit and only its answer is withheld (such a member holds the TSIG secrets and could send a native UPDATE). The rcode is acknowledged inside the member request's command output scope (an empty member command after the zone runtime's own commit). The follower relays that rcode, signed with the request's key, under an acknowledgment bound to the verified key and unchanged empty response rather than its own data generation. A command that was not sent, was refused by member admission, or whose exchange was lost answers SERVFAIL and is never retried. Fenced, conflicted, standby and static nodes keep their local SERVFAIL. | The v0.2 UPDATE row requires primary routing once follower mode exists. Followers sit behind the same VIPs and DHCP configurations as the primary. DNS has no rcode for "outcome unknown", and RFC 2136 section 4.5 tells the requestor to try its next server on SERVFAIL, which is safe for an unsent update and is the native primary's answer for a committed but unpublished one. The receipt ledger already deduplicates by retry identity, and the zone runtime commits in its own fenced transaction, so the member command adds no second dedup row. | Refusing on followers with REFUSED or NOTAUTH (clients would have to find the SOA MNAME, and REFUSED claims a policy refusal); trusting the follower's grant check; re-verifying the MAC on the primary (adds nothing against an mTLS-authenticated enrolled member, which holds the same keys); REFUSED while the primary is unreachable (stops RFC 2136 clients from trying the primary); retries, local fallback or replay after reconnection; a generic DNS proxy |
