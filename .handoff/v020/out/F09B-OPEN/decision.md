| D384 | Kubernetes integration root: one source head per Integration UID, per-object ledger CAS, Lease verified before each effect, replica-side source runtime, holder-only commands, a root-armed cleanup finalizer, publishers halted on a reported source conflict, and refusals republished with backoff | On Kubernetes the integration host runs on every replica and elects one Lease per Integration. **What is atomic:** (1) a source commit is one create or one exact-resourceVersion update of the `IntegrationSourceHead` of that Integration UID, sequence n to n+1, never retried, inside the host's source scope after its final check and the root's fence; the immutable `IntegrationSourceChunk` Secrets it references are staged by fenced create-only writes and rechecked as durable before that write, so a lost head CAS changes no source and leaves only unreferenced chunks; (2) each ledger, operation, budget, delivery and event-cursor write is one create-only or exact-resourceVersion Secret write, never `Force` and never repeated with a fresh version, and only those private kinds can be written or forgotten through the ledger seam; (3) name-allocation exclusivity per scope and label; (4) each Integration status write, by the Lease holder, with the captured resourceVersion as precondition; (5) each finalizer change, one metadata patch bound to the observed UID and resourceVersion; (6) on each replica, the swap of the whole inventory and MAC-grant set derived from the heads it read. **What is not atomic, and how it is compensated:** (a) the Lease is a rejection check, not a lock: before each provider request and each store write the root reads the Lease live and refuses unless it still names this replica with the holder, acquire time and transition count recorded when the term started and an unexpired renew time; a request or write already sent after a passing check can still land after the Lease is lost, and is then a serializable predecessor of the successor's CAS or a conflict; the proof assumes one live process per identity, and the identity is the node name, so two live processes that share it both pass it; (b) guard versus write: the Integration's UID, resourceVersion, mode, suspension and spec digest are compared by a live read just before each write, not in the write itself; a publisher's captured source zones and record sets are compared against the replica's watch snapshot by UID and identity (everything but status, resourceVersion and managed fields); contributed ClientGroups are read live by UID and identity just before the head write; a change that lands in between is caught by the next fence, by every replica's eligibility check at consumption, and by the ledger's pending-intent recovery; (c) a forget of several ledger rows, the retirement of replaced chunks and a Delete purge are sequences of exact UID and resourceVersion deletes that stop at the first failure (a purge removes source-owned objects, then the head, then chunks, allocations and deliveries, so a cut purge leaves a suffix the next run removes; a failed chunk retirement leaves an unreferenced chunk that no source uses); (d) inventory and MAC grants are derived on each replica from the committed heads it last listed (every 10 s and after its own commit) and its own object snapshot: the Integration must have the head's UID, not be suspended or deleting, run on this store and have the head's spec digest, and every target and evidenced object must match by UID and intent digest; eligible sources are rebuilt in one canonical order (accepted time, then source ID), so replicas that read the same heads arbitrate alike, but the cross-source removal watermarks SQLite persists are not durable here; "published" means installed on the committing replica; a failed relist keeps the last listing, so answers continue until each observation's original expiry and are never renewed; (e) remote provider effects, as on SQLite. **What runs:** Cloudflare publication, UniFi inventory and VLAN/note groups (no `spec.unifi.inventory`), the `deletionPolicy: Delete` cleanup and the administration API, for Integrations in the release namespace only (the file and environment credential allowlists are node-wide; another namespace is refused with `NamespaceNotAllowed`). UniFi record publication is refused with `RecordPublicationUnsupportedOnKubernetes` (source-owned DNS children are not certified on this store yet) and webhook instances with `UnsupportedOnKubernetes` (hook events read SQLite's change feed). An instance refused outright has its credential references left unresolved (`ih.Input.WithoutCredentials`), so no keyed fingerprint of an allowlisted credential reaches its status. A refusal status that could not be written is retried by a new term no earlier than one poll interval after the first failure, doubling per consecutive failure up to five minutes, and nothing wakes the host early, so a status write that keeps failing costs at most one Lease term, one capture and one write per backoff step (the earlier "at most once per poll interval" claim was false: the failed write woke the host and looped). **Source conflicts:** while the controller reports any admitted record set `Duplicated`, `Occluded` or `Invalid` for its current generation, every publisher is refused with `SourceConflicted` and a message naming up to five of them, written on its object by its Lease holder; observers and refused instances keep running; the host asks `Refuse` after every capture and replaces a job whose answer changed, so a running publisher is stopped and joined when a conflict appears and restarted when it clears; a conflict reported after a capture fences the next effect, because `check` reads the conflict conditions of each captured record set from the live snapshot (the source identity still leaves status out). One bad record set halts every publisher, not only those that select it: a publisher plans from its whole selection, telling which ones select it would mean repeating each provider's zone, label, type and exclusion rules in the root, and dropping the record set from the selection would let a `sync` publisher delete its remote copy; anyone who may create a record set a published zone admits can therefore pause Cloudflare publication, which the operator guide says. **Administration:** list and get read the Ready condition the Lease holder wrote, known only when it observed the current generation (an instance no job runs for shows the status every replica derives from the same revision); check, preview, sync, actions and act run only on the Lease holder with the exact reviewed UID and revision, and any other replica answers 503 with the holder's name, never forwarding or replaying; the route permission is checked once per request, with no original-credential re-authorization inside each effect; a reviewed sync or act and a cleanup or release summary are structured log lines, because this store has no kudurru audit table; the release command removes the reserved finalizer by exact UID and resourceVersion. **Delete:** the root arms the reserved finalizer on every live Integration that runs here with policy `Delete` (licensed) and disarms it when the policy changes, by metadata patch from any replica (losers conflict); until a capture shows it the host pauses the instance and every fence refuses it; an instance the root refuses outright is never armed and reports its refusal instead of pausing, because it never runs a provider and owns nothing. A lost shared request-budget CAS writes nothing; the request makes fresh reservation attempts, each after a jittered pause doubling from 10 ms to at most 250 ms and its own fence (a reservation is commutative and idempotent by ID, D364), until one is written or the request's own context ends (its operation timeout, or lease or job cancellation), and no request is sent unreserved; without them instances starting together on two replicas collided on the budget's first write and a loser's setup failed, leaving it inert until its object changed, and a fixed bound of four attempts still left one of four instances inert. Native Secret credential references stay disabled. Supersedes the statements that Kubernetes "cannot use sequential per-object writes" for this root. | Kubernetes has single-object CAS and no multi-object transaction. The source format is already content-addressed chunks plus one head pointer sized for Secret carriers, and the outbound ledger already serializes every effect through one object per record, so one head CAS is a real commit point and the per-object ledger CAS needs no wider transaction. This is not D239's rejected "sequential writes pretending to be atomic": the only multi-object steps are ordered so that every intermediate state is a valid one, and every non-atomic seam above is named with its compensation. Deriving consumption on every replica from committed heads keeps the query path free of store reads and leaders. Holder-only commands keep the host's command capture exact; naming the holder is honest where forwarding would replay. Arming by the root closes the gap left by the absence of admission without an elected step, because a finalizer patch is idempotent and exact. | Strict root-gated serving that hides uncertified source-owned records from every DNS consumer (cross-cutting, exceeds SQLite parity); mounting the SQLite lifecycle runtime on Kubernetes (D366); sequential per-client writes as the commit (D239); Leases as locks; a budget re-reservation with a fixed attempt count (four attempts left one of four instances inert) or one without a deadline, or one inside `ReserveBudget` (the ledger keeps its single-CAS rule; the deadline-bounded re-attempt is the host's fresh explicit reservation that rule asks for); native Secret references in the release namespace; running Integrations from every namespace; forwarding a command from a non-holder replica (a forwarded uncertain effect could be replayed); persisting cross-source inventory watermarks in a cluster-wide Secret (another CAS hot spot written by every source); arming the finalizer only from the elected job (stalls the first publication behind a self-made resourceVersion change); repacking UniFi per-client record sets into bounded integration-owned record sets in this release (fixes a capacity layout that later cannot move); a per-process nonce in the Lease identity; halting only the publishers whose selection contains a conflicted record set (repeats provider selection in the root); publishing the selection without the conflicted record set (a `sync` publisher would delete the remote copy); keeping a reported conflict as an unavailable capture with no reason on any object (SQLite's behavior, silent on Kubernetes); retrying a failed refusal status on the next wake (a hot loop under a persistent write refusal) |
