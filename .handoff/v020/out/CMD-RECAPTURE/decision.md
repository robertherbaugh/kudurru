| D399 | Commands superseded before dispatch | A current HTTP command (`currentAuthCommandThen`, `currentAuthCommandOutput`, so sign-in, sign-out, cluster activation and join-token, object, zone and settings writes and every other route on that path) that is refused with `serving.ErrPending` before its transaction body began, only because another commit superseded the publication its request captured, captures the current publication again (`servinghttp.Recapture`) and is dispatched once on it. The wait is bounded by 5 s (the import step's cut wait) or the request deadline, whichever ends first; then the answer is the existing effect-free `503 unavailable`, now with `Retry-After: 1`, which is set only on a refusal returned before any transaction body of the command began. Only a request none of whose commands has dispatched captures again (after its own first commit a request stays held to its publication). The new capture is admitted only when its authority equals the original one advanced in its installed revision, its auth view has the same dependency identity (license, permissions, role bindings, keys, providers, auth overrides), the same auth controls and the same cluster settings object (a settings merge prepared from the original settings must not overwrite a newer one), and the original raw credential verifies on its auth view as the same principal, with the same session (ID, CSRF secret, issue and absolute expiry) and the same effective roles; the transaction then repeats its authorization and source checks against it. The request keeps every lease it held until it ends. Never retried: a refusal from inside the body or at commit, an uncertain outcome, a later item of a multi-item request (D378 chain), a fence or authority change, a changed credential, session or role. A command whose reviewed source digest is compared only outside its transaction (`join-token`) captures again only on the same source generation (`WithExactSource`); activation compares it in its transaction and answers `409 conflict` for a stale review. Follower early admission, follower-forwarded commands and promotion keep their binding; the primary's forwarded-command entry is bound to the member request's authority, not to a publication. An integration operation's first no-op holds the integration host's lease barrier and runtime lock and is marked `WithoutRecapture` (immediate refusal). A request refused at capture before it is read (`503 generation_pending`) is not covered. Signed RFC 2136 UPDATEs are not recaptured. | Nothing was dispatched, so capturing again is not a replay and leaves "no replay of a refused or uncertain mutation" and "explicit outcome unknown" untouched; the refusal only told the caller that the node had published its own work meanwhile, which a ready node does for seconds after every write. Doing it once in the shared command path covers every route, as the import step precedent (`fix(imports): recapture a superseded cut before a step dispatches`) did for migrations. An UPDATE's capture is the DNS transport's: its keyring verified the signature and its output signs and sends the answer, so a new capture would verify and admit the same wire message on a second keyring; the UPDATE half is a decline, not a fix (its pre-dispatch SERVFAIL and the withheld acknowledgment of D313 are unchanged). | A client retry policy on `503 unavailable` (moves the problem to every client and the dashboard, and a client cannot tell a pre-dispatch refusal from others); re-running the whole handler on a new lease (the body is consumed and handler work outside the transaction would repeat); per-route recapture (misses routes); an unbounded wait (a node that keeps publishing would hold requests indefinitely); recapturing UPDATEs or forwarded commands (rebinds signature verification or the follower's source). |
