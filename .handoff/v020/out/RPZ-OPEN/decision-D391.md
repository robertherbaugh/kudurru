| D391 | RPZ feed diagnostics | Per-node RPZ feed state is read from the node's `rpz.Manager` at request time and exposed on both drivers through `GET /blocklists/_rpz?namespace=` and `GET /blocklists/{namespace}/{name}/rpz` (both `blocklists.read`; 501 without a manager, 404 when the node's configuration snapshot has no such list, 503 before any snapshot), `kudurru lists rpz [name] [-A] [-o wide|json]`, one `/info/messages` diagnosis (source `rpz`) per feed that is pending, serving with a failed refresh, expired or unavailable plus an `RPZRulesIgnored` info per feed with ignored owners, and scrape-time `kudurru_rpz_feed_*` gauges labeled by list and source. Each item derives one `state` (`pending`, `serving`, `expired`, `unavailable`) with a reason and message, and carries serial, primary, confirmation, expiry, next attempt, bounded last error, compiler totals, compiled rules by trigger and action, and every ignored reason with its complete count (the compiler now counts per reason beyond the 32-sample cap) and up to five example owners. The serial and counts stay visible after expiry. `expired` is reported only once the copy's absolute expiry has passed at the manager's observation time (`rpz.Status.Expired`); an unexpired copy that cannot be used because it was confirmed after the node's clock is `unavailable` with reason `RPZTransfer` and keeps its copy fields; a copy the manager discards because configuration or credentials changed during acceptance is dropped together with the status fields that describe it (serial, counts, rules, ignored owners, primary, confirmation, expiry), so it is reported as `unavailable` with no copy fields and no `RPZRulesIgnored` (RPZ-OPEN). Every state but `serving` answers SERVFAIL for a selecting policy, `pending` included; the `pending` diagnosis stays `info` on purpose. | The manager already held everything an operator needs to know why a feed answers SERVFAIL, but nothing outside the package read it. Feed copies are per node, so the answer must name the node and never be presented as shared BlockList status; a dedicated route keeps the BlockList object read free of node-local state. Reading at request time matches the other operational diagnoses and needs nothing on the DNS path. Every newly configured feed, and every feed on a node starting without a stored copy, passes through `pending` until its first transfer, so an error there would make `kudurru doctor` fail during every healthy rollout of a feed (stub zones treat pending the same way); a first transfer that fails moves the feed to `unavailable`, which is an error. | Adding feed state to BlockList `status` (shared object, would claim one node's copy for the cluster); adding it to the dig explanation only (shows one feed per hit, not why a feed is down); fanning out to every node from one request (new forwarding path; per-node reads with the node name are enough); exporting the primary or error text as metric labels (unbounded cardinality, may carry addresses); a single total for ignored owners (hides which unsupported trigger a vendor uses). |
