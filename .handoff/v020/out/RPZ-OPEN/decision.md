| D390 | RPZ feeds on the Kubernetes driver | Every Kubernetes replica runs the same `rpz.Manager` as SQLite, persisting accepted copies in `local.db` and acquiring with the stored TSIG startup source and its hot replacement (D314/D365) through a new per-feed `CaptureZoneKeys` hook, so an unsigned feed is admitted while stored keys are pending and a ring replacement wakes the manager. The blocking stage gets a Kubernetes selector (`kubeRPZ`): `policy.ListInfo` now keeps the accepted BlockList it was compiled from, so each recursive query takes the BlockLists of its own policy decision and selects them from one immutable binding of the configuration snapshot, the node's feed snapshot and the published ring. The binding is rebuilt only when one of those three installations changes; every input is an in-memory atomic read. A missing, unbound, rotated or expired feed, or a stale configuration snapshot, stays selected as an unavailable sentinel and answers SERVFAIL with EDE "not ready". The manager is not leader-only. A restart while the apiserver is unreachable cannot read the stored TSIG keys (the startup source has no local fallback), so only unsigned persisted copies are reused; a signed feed fails closed until the pod restarts with the apiserver reachable. A referenced BlockList that exists but is not compiled yet is carried in the policy decision (`Decision.PendingBlockLists`) and both drivers' selectors require its feeds, so a just-started node applies a persisted copy or fails closed from its first answer, whatever `blocking.allowDegraded` says; with `allowDegraded: false` the node also stays not ready until every referenced list is in the policy, because the zone cache reports ready on a `local.db` start only once the snapshot built from `local.db` is published (RPZ-OPEN).  An unsigned feed's persisted copy is reused on a restart without the apiserver and without its primary (proven by the mounted test). | The CRD accepted RPZ sources on Kubernetes and promised fail-closed behavior, but no manager ran and the stage had no selector, so an RPZ-only list compiled to an empty list and the feed was silently unenforced. Kubernetes has no complete serving bundle to bind feeds into, so the binding has to start from the request's own policy decision; carrying the object in the Index avoids looking lists up in a newer snapshot than the decision. Rebuilding only on installation change keeps per-query cost at the SQLite path's `Select`.  The feed comes from the manager, not the list resolver, so waiting for the resolver to compile an RPZ list only opened a window in which a blocked name resolved NOERROR; the zone cache had switched to `local.db` before publishing it, so the empty unsynced index (which references no list) satisfied readiness for about 100 ms. | Documenting the load window instead of closing it (left a fail-open window that `allowDegraded: false` promised to prevent); gating every query on list compilation when `allowDegraded` is false (would SERVFAIL all clients whenever any download list fails); refusing RPZ sources on Kubernetes at admission (drops a v0.2 row on a supported driver); running feeds only on the leader and fanning out (puts a leader on the DNS path); looking the decision's lists up by name in the current snapshot (can mix two configuration generations); binding on every query (repeats credential fingerprinting per query); flushing the edge dnsdist cache on every feed installation (SQLite does not either; left as a follow-up); reusing a signed persisted copy offline by its stored credential fingerprint (would admit a credential the node can no longer verify as current; left as a follow-up). |
