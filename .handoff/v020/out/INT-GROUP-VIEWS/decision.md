| D403 | Client-group record views (split horizon) | An endpoint whose `kudurru.view` names a ClientGroup (in the record set's namespace, as Policy `clientGroupRefs` do) is served only to that group's clients, on both drivers. A zone with views is built as its default zone plus one complete variant per group (at most 16): a view RRset replaces the default RRset of the same name and type, a view CNAME replaces everything at its name and any view RRset replaces a default CNAME; views never remove a default name, but a view name and its empty non-terminals exist in the variant, so a default wildcard does not synthesize answers there for the group. A view may replace only default data its own namespace claimed (same name and type, or a CNAME on either side); one that would replace another namespace's default data is `Duplicated`, so the cross-namespace ownership rule of default endpoints also holds for views. View identities are keyed by the ClientGroup ID (`namespace/name`). Other clients get the default zone's answers, including NXDOMAIN/NODATA with the default SOA for view-only names. The authoritative stage picks the variant after the zone match and query ACL (`Zone.ForGroups`: no store read, no allocation, the zone itself without views); a client in several groups with views of one zone gets the group that sorts first. Views hold leaf data only (no NS, DNAME, SOA, DNSSEC types, no apex CNAME), are refused (`Occluded`) at or below a delegation or DNAME, and are not served in a DNSSEC-signed zone (`spec.dnssec.enabled` or RRSIG/NSEC/NSEC3/DNSKEY in the default data; the endpoints are reported `Invalid`). On SQLite the compiler applies both checks to the dynamic (RFC 2136) records of the committed head too, so a view never reaches a commit the committed build would refuse (D373). The 16-view budget is per zone and shared, in build order, by every record set that feeds it (a known limit). Transfers (AXFR/IXFR, journal, NOTIFY), exports, RFC 2136 UPDATE (prerequisites and writes) and integration sinks see the default data only; on SQLite the committed aggregate stores views in a separate `views` list and a static view endpoint still reserves its name against UPDATE. The content hash covers views, so a view change advances the serial. Any group view, desired or still served by a committed model, makes kudurru report `zone-client-view` and the edge bypass both its authoritative and resolver packet caches. The CRD schema restricts `view` to `public` or a DNS-1123 subdomain name. | The field promised group-scoped answers but every such endpoint was silently withheld. Full per-group variants reuse the existing lookup (wildcards, CNAME/DNAME chasing, negative answers, glue) unchanged, so the query path gains one pointer selection instead of a second lookup algorithm; keeping views out of the default tree and the committed `records` means every consumer that does not know about views (transfers, journal, UPDATE, export, sinks) is safe by default. dnsdist's packet cache keys on the question and cannot tell groups apart, so bypassing is the only leak-free edge behavior. | Overlay lookups that consult the view tree first at every step (wildcard, ENT and CNAME semantics would need view-aware rewrites of lookup); merged views for clients in several groups (exponential prebuilt combinations or per-query allocation); transferring a view selected by TSIG key, BIND-style (no secondary contract for it yet); serving views in signed zones (needs per-view signatures and denial chains); rejecting group views at admission and deferring them (leaves split horizon unavailable in v0.2); letting any namespace's view override any default name (a namespace could redirect another's names for every client its ClientGroup matches); a per-namespace view budget (needs a second bound and admission ordering across namespaces; deferred). |
