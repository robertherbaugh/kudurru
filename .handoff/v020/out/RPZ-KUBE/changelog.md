### Added

- RPZ feeds now work on the Kubernetes store driver. Every replica transfers RPZ BlockList sources (signed with stored TSIG keys or unsigned), keeps an accepted copy across restarts, and enforces QNAME, CLIENT-IP and RESPONSE-IP triggers with NXDOMAIN, NODATA and TCP-only actions, logging `blocked_rpz` in the query log. Other actions (DROP, PASSTHRU, local data) use the same blocking stage as SQLite. Running replicas keep enforcing through leader changes and apiserver outages. A replica that restarts while the apiserver is unreachable reuses only unsigned feeds: a signed feed cannot read its stored TSIG key, so clients whose policy selects it get SERVFAIL until the replica restarts with the apiserver reachable.

### Fixed

- On Kubernetes an RPZ BlockList source was accepted but never transferred or evaluated, so the feed was silently unenforced. A selected feed that is missing, expired or bound to a rotated key now answers SERVFAIL (Extended DNS Error "Not Ready") instead of being skipped, and so does every selected feed while the node serves a `local.db` snapshot older than `store.kube.snapshot.maxAge` (forwarding stops for those clients, not only primary zones). As with every list, a just-started node applies an RPZ list only once it is compiled (a few hundred milliseconds measured); until then the feed is skipped, not failed closed. With the default `blocking.allowDegraded: true` the node is ready during that window; `allowDegraded: false` keeps it not ready on a normal start, but readiness only steers traffic, and a restart from `local.db` without the apiserver was still seen answering unfiltered for about 100 ms.
