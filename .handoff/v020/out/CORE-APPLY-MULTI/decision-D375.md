# Corrected D375 row (follower requests), for CORE-APPLY-MULTI

The forwarding lane's row "Multi-item requests through an enrolled follower"
(`out/HA-FIX/decision.md`, row 2, to be numbered D375) is unchanged in what a
follower does. D378 changes two statements of its "why" cell and adds one
rejected alternative:

- The reason "the original-source rule forbids continuing a request across a
  source change" now holds for a follower only; on the primary a request
  follows its own commits (D378). The row says why a follower cannot.
- "`kudurru apply` is idempotent and can be run again" is replaced. Measured
  runs (`evidence/DOCS-OPS/verify-r3-follower-ha01.log`: twelve repeats of a
  250-document file through a follower created nothing more) and the code
  (`internal/cluster/replica/command.go`: every new forwarded command commits a
  deduplication record) show that repeating a cut file through the follower
  does not finish it.

The complete corrected row, in place of the original one:

| D375 | Multi-item requests through an enrolled follower | A follower bounds one 30-second lifetime, before body read, for every route whose effect it forwards as `objects.write`, `objects.delete` or `zones.command`: the `/objects` routes, `POST /apply`, the `/blocklists`, `/clientgroups` and `/policies` routes, `POST /{kind}:batchDelete` and the four zone convenience commands (25 registered routes, named by one predicate; a test observes which registered routes reach the forward hooks and holds the predicate to them). Every other `POST`, `PUT` and `DELETE` under `/objects/` and `/zones/` keeps the same bound on a follower, as it had before the predicate (`POST /zones/{zone}/notify` is the only registered one; it is not forwarded). `POST /apply` and `:batchDelete` send one member command for each document or name, in order, inside that single lifetime and keep their ordinary `200` answer with one result for each item. An item is reported with `unavailable` and its cause, is not applied and is never replayed when the lifetime has ended, when the request was canceled, or when the follower's own installed source changed since the request began (its next pull, five seconds by default, usually installs the request's earlier items). A request that began on a follower stays a forward after its context has ended: `ObjectForward` and `ZoneForward` read the mode of the request's original lease (`servinghttp.SourceMode`, which returns no token) and answer that refusal themselves instead of falling through to the node's local command. An item whose exchange with the primary fails keeps the answer of a single forwarded write, `completion_unknown`: the member client treats every failed POST exchange, including an unreachable primary, as an unknown outcome. Earlier items stay committed. There is no document cap and no new status. A capture refusal names its cause (source changed, lifetime ended, canceled, route not forwarded) instead of always reporting a changed source. | D362 already claimed `kudurru apply` and the dashboard editors, but only `/objects/` and `/zones/` paths were bounded, so capture refused every other route and reported a changed source. Apply and batch deletion already define per-item results on every node. The primary lets a request follow its own commits by an exact compare of command receipts (D378). A follower has no such receipt: the image that its pull installs does not say whose commands it contains, so the original-source rule (capture once, never retarget) still forbids continuing a request across a source change there, a partial result is the honest outcome and the items say exactly what happened. Running the apply again through the follower does not finish a file that was cut: the follower forwards the committed documents again, the primary commits a deduplication record for every forwarded command, also one whose result is `unchanged`, and the follower's next pull changes its source again. Such a file goes to the primary, which applies every document in one request. Before the review fix an ended request fell through to the local command, whose credential check answered `401 unauthenticated`, "current credential is invalid or expired", for a write that had only run out of time. | A typed `413` document cap for follower requests (an arbitrary number that would refuse applies that fit, and that would not remove the source-change cut); a longer or per-item lifetime (extends the original request bound); re-capturing a new source for later items or retrying a refused item (retargets or replays a decision); making apply atomic across documents on a follower (it is not atomic on the primary either); chaining a follower's later items on the primary's receipts as D378 does on the primary (the member protocol returns a result, not a commit receipt, and the follower would have to accept an installed image for a request that began on another one); a blanket 30-second bound for every unsafe follower request (would cut node-local work such as lease import or query-log purge); bounding only the forwarded routes (takes an existing deadline away from the other unsafe requests under `/objects/` and `/zones/` for no gain); letting `SourceToken` answer for an ended context (hands a comparison token to a request that may no longer act); deciding the role from the Store's current authority instead of the request's lease (samples a replacement source) |
