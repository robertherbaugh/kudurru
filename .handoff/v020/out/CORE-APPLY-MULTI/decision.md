# CORE-APPLY-MULTI decision row (D378)

One row for the decision log, in the existing format. A corrected complete row
for the forwarding lane's follower decision (to be numbered D375) is in
`decision-D375.md` next to this file.

| D378 | Requests with several items on the node that owns the commits | On the complete SQLite runtime `POST /apply` and `POST /{kind}:batchDelete` still run one current command for each item with the request's original credential, lease, elected writer episode and lifetime, and declare one command chain of the provider coordinator for the request (`ObjectItems`). Until one of the request's commands has completed, each is admitted on the original lease exactly as a single command is. The first completed command anchors the chain: on its own commit receipt, which the Store issues in the command's finalizer under the writer lock (`sqlite.CommandReceipt`), or, when it changed nothing, on the coordinator's mark at that moment. Every later command is admitted under the publication gate only while the coordinator's mark of the last command that changed canonical state is still the chain's anchor, compared by identity; it also requires the original writer episode and a Store authority equal to the lease's own in every field except an advanced installed revision, and it reads the raw credential, grants, ownership, preconditions and limits again in its transaction. A foreign commit is a state-changing command of anyone else through the coordinator: a public API mutation under any credential, including a sign-in, a member command forwarded from a follower, an operator-started integration operation, a migration step or the unblock-request sweep; a command whose SQL outcome is unknown counts as one. Writers outside the coordinator, which take only the Store lock or the primary pin, are not detected and do not stop a request: the node's own follow-up work (status reconciliation, the zone lifecycle and its heads, list fetch status, integration reconciliation, the RoleBinding objects source, the login-lane request charge and provider authority admission) and two writers that act for another party, RFC 2136 updates under a TSIG key and commands of the local admin socket. This is accepted as the rule: each item reads everything it is admitted on again in its own transaction, so an undetected write can change only what a later item finds, never what it is decided on. Replacements of node-local dependency installations between two items are not compared either; each command pins the current ones. Because every commit retires the publication that local DNS answers and every other API request are bound to, a request whose items have run for two seconds since the node last had a current publication for it lets the next item first wait, inside the request's lifetime and writer episode and for at most two seconds, until the publisher is current again (`Publisher.WaitTerm`), and then commit nothing for 200 milliseconds; a wait that reaches its two seconds goes on without the publication and without the rest, so the pace makes a request at most about twice as slow and cannot by itself run it out of its lifetime; the wait captures no lease and admits nothing, so the chain compare still decides and a foreign commit in the pause stops the rest. After a foreign commit every later item answers `unavailable` ("another change was committed on this node while the request ran"), is not applied and is never admitted again; earlier items stay committed. An item reached after the request's lifetime ended answers `unavailable` with that cause. A follower keeps D375: it forwards each item as its own member command and never uses the chain. Kubernetes has no such gate and is unchanged. | Every commit retires the lease that the next command's admission compares against, so one request applied only its first new or changed document and refused the rest with `unavailable` ("current writable serving generation unavailable"): a three-document `kudurru apply`, an eight-document `kudurru restore` into a new node and the dashboard's multi-delete each needed one run per document (mounted reproduction retained). No item is decided from the request's image: everything an item is admitted on is read in its own transaction. What the lease comparison added between two items is that nobody else had acted; an exact compare of command receipts keeps that for every command through the coordinator, but not for the writers outside it listed above. The node follows each commit with its own status and lifecycle writes within milliseconds and replaces provider resource sets on its own schedule, so a compare against the exact generation of the previous item, or against the lease's dependency installations, cuts a request at an arbitrary item (a mounted restore stopped at its fifth document). Unpaced, the items of one request commit back to back and the node has no current publication for the whole request: in a review probe on a loaded machine one apply of 300 documents left an existing local record unanswered for 27.5 s and other callers got `503 generation_pending`; the pace bounds that to about two seconds plus the node's time to publish, at the cost of a slower long request. | Capturing a new lease for each item, as migration programs do (D223) (waits for one complete publication per item and admits an item after any foreign commit); admitting item N+1 only at exactly the generation that item N produced (the node's own writes follow every commit and the publisher skips generations, so that generation is rarely published); tolerating any commit after the request's first one (a foreign decision between two items would go unnoticed); classifying every commit in the Store by kind or by status-only content (a table of every present and future kind, and private zone state is neither status nor desired state); requiring the lease's dependency installations for the whole request (the first provider reconciliation cuts a long request, and nothing is decided from them); holding the publication gate across all items (stops publication and every other writer for the whole request); an unbounded wait for the publication (under heavy load one request of 120 documents ran out of its five-minute lifetime); no pace (one request withholds local DNS answers and refuses every other caller for up to its five-minute lifetime); a shorter work budget (150 new record sets took 26 s instead of 3.9 s with half a second); installing a coordinator mark from RFC 2136 updates and the admin socket (more cut requests for writes an item rereads anyway); one transaction for the whole request (changes the per-document contract; one invalid document would fail a restore); relaxing the single-command check (weakens every other route); chaining a follower on the primary's receipts (needs receipts and preconditions in the member protocol and a different install rule) |
