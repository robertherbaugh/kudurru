| D385 | Effective zonegroup scope | A zone group is a DNSZone label: `kudurru.io/zonegroup: <group>` (`v1alpha1.ZoneGroupLabel`), so a zone is in at most one group and an unlabeled zone is in none. A binding, frozen grant or API-token scope `zonegroup:<group>` covers a zone attribute whose stated group equals `<group>` (`rbac.Scope.Admits`); routes keep presenting cluster and zone scopes only, and `rbac.Attributes.ZoneGroup` carries the group. The code that reads the zone states it from the same source: the API router (`Server.authorize`) from the request's captured publication on the complete SQLite runtime and from the store on Kubernetes, only when the decision without the group is a denial (`Admits` only adds coverage), at most once per zone per request, and from the listed objects in zone lists; a follower's early forward admission from its captured cut; every SQLite command reauthorization (`ReauthorizeCurrent*`, `ReauthorizeOperationCurrent`) discards the caller's value and reads the DNSZone again in its own transaction. An absent or unlabeled zone has no group, so a group binding grants nothing for it; a zone that cannot be read answers 503; cluster and zone bindings never depend on the label. Adding, changing or removing the label is an access-control change: a DNSZone write that changes it needs `zones.write` at cluster scope on both drivers. On Kubernetes the store write decides that rule again on the read it compare-and-swaps against, and a label change through the API is a forced whole-object takeover (other field managers' ownership moves to `api`), with the written label checked (409 when it still differs), so a removal never answers 200 while kubectl's ownership keeps the label. `GET /zones` reports `zoneGroup`; `GET /auth/me` reports `scopedPermissions` keyed by scope (`zone:<name>`, `zonegroup:<group>`). RoleBinding admission, and `rbac.bindings` at start (the same `Validate`), refuse a zonegroup name that is not a valid label value. | The design record names `zonegroup:<label>` (§8.5); a label needs no new kind, CRD field, store index or replicated state, and Kubernetes users can set it with kubectl. Resolving the group where the zone is read keeps `Scope.Covers` and every authorizer pure, reuses the existing capture-then-recheck-at-commit pattern, and makes a label removal or binding removal deny the next command without a cache. Requiring cluster scope for relabeling stops a group or zone admin from handing a zone to another group. | A ZoneGroup kind listing member zones (new CRD, a second object to keep consistent, no transaction across objects on Kubernetes). Multi-valued membership via one label key per group (`zonegroup.kudurru.io/<g>`): harder to reason about and to show in the UI. Resolving the group inside each authorizer with a zone lookup callback: the SQLite auth cut holds no DNSZones, and the Kubernetes and SQLite authorizers would read different sources from the zone the handler serves. Trusting the router-stated group at commit: a follower or an earlier cut could widen a command. Allowing whoever may edit a zone to change its label: lateral handover of zones between groups. Forcing ownership of the label key only: needs a per-field takeover in the store contract; the whole-object takeover already exists and matches a whole-object PUT. Refusing a label change on a zone other managers also own: an administrator could then never revoke through kudurru. |
