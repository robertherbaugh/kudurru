What now happens.

**Served record rows (defect).** On the complete SQLite runtime `GET /zones/{zone}/records` lists the served zone. Its rows named no record set, so Edit on a served client-group view of a non-default namespace saved into `default/api-<zone>` (the editor fell back to the default record set): `kids/lan` was written as `default/lan` while the dialog showed `kids/lan`. An edit of any served row held by another record set added a second endpoint, which the builder refuses as Duplicated, instead of changing the served one. A served row now names its record set, manager, set identifier, comment and labels when exactly one live (not disabled, not expired, not `public`) desired endpoint of the request's captured objects (`ZoneReads.ZoneObjects`, the same cut as the served model) has its owner, type and view; a view is looked up only in its ClientGroup's namespace (`internal/api/zones.go` `servedOwners`). System data (SOA, apex NS), dynamic data (RFC 2136 UPDATE, DHCP) and an endpoint held by several record sets (set identifiers, `mergeStrategy: union`) still name none. This narrows the earlier rule "a served RR is never given a desired owner" to "only a unique desired identity proves one"; the existing guard tests (`TestCapturedZoneReadsSummaryRecordsExportAndOwnership`, the mounted `dynamic UPDATE record was assigned invented desired ownership`) still hold and were not changed. The dashboard edits a served row in the record set it names, keeps a view row's namespace when it names none (`<ns>/api-<zone>`), and withholds Edit from a served row that names no record set, with the reason. Delete of a row that names a record set is limited to that record set; otherwise it is limited to the group's namespace (view) or spans the zone (default data), as before. `remapView` no longer turns a bare group name into another namespace's group when the record set's namespace is edited in place (the remaining half of the verifier's "Served to goes stale" finding).

**The list says which list it is.** `GET /zones/{zone}/records` answers `ZoneRecordList` with `source: desired | served`; the dashboard's `listsServed` reads it instead of inferring it from empty record sets (that inference would now be wrong).

**CLI.** `kudurru records add --view public|<group>` stores `kudurru.view` (`--view -` is refused: leave it out for the default data) and says who the record is served to; `records rm --view -|public|<group>` removes one view; an explicit `-n` narrows `rm` to that namespace's record sets (without `-n` it still spans every namespace, as before); `records list -o wide` has a VIEW column (`ns/name` outside the default namespace). The CLI reference is regenerated.

**IAM.** `GET /iam/users` and `GET /iam/serviceaccounts` carry `managedBy` (also the create and update answers of a local account, and the auth stack's lists). Local accounts and service accounts of another manager show their change actions disabled with the reason ("Declared in kudurru.yaml…", "Created by the bootstrap…", "Managed by system…"); the dialogs' own check and the server's 409 stay. A service account row has **Tokens…**: `GET /auth/tokens?all=true` filtered to that account (owner kind, namespace and name), each token revoked after an in-dialog confirmation with one `DELETE /auth/tokens/{id}` through `useIamCommand` (sent once, locked after a refusal or an unknown outcome). Listing needs `tokens.read` and revoking `tokens.delete` (`useCannotReason`: permission, static mode, follower). The role binding form edits every subject (up to 256) in stored order, adds and removes subjects and refuses an empty list or a duplicate before sending; the multi-subject refusal on the row and in the dialog is gone. The role binding and token-revocation unknown-outcome text no longer names the revocation-record limit (`iamUnknownText(what, floor)`). `docs/guide/dashboard/identity.md` now says exactly which rows are disabled (accounts and service accounts of other managers, role bindings of other managers; `rbac.bindings` rows have no actions; an IdentityProvider object of another manager keeps its row actions and is refused in the dialog).

**RPZ polling.** A settling feed read (404, 503, or a feed not serving) keeps 3 s for two unchanged reads, then 6, 12, 24 s and 30 s (`rpzSettlingDelay`); a change of a feed's state, serial or reason, or of the error, restarts the fast reads. A read is counted once by its update time because React Query evaluates `refetchInterval` on every observer update. Applies to the Lists page (`GET /blocklists/_rpz`) and to a list's feed section.

**Integrations batch delete.** The list selects the rows the API may delete (manager allows it, not terminating) and deletes them with `POST /integrations:batchDelete`, one request per namespace, one at a time, after a confirmation naming each instance's deletion policy. No new route; `batchDeleteIntegrations` was already in the follower contract, the refusal inventory and `src/lib/follower.ts`.

No route was added or reclassified, so the follower contract, its pinned counts, the permission table and the refusal inventory did not change. A lane's manifest field limits in `src/lib/integrations.ts` were not touched.
