| D394 | CLI for stored TSIG keys | `kudurru tsigkeys list|create|replace|reseal|revoke` drives the `/tsigkeys` routes on both drivers. The secret comes only from `--secret-file` (a path or `-` for stdin), is checked locally as canonical base64 of at most 512 bytes (whitespace ignored), and is never printed, since the server never returns it. Replace, reseal and revoke take the exact `--uid`/`--resource-version`. `apiclient.TSIGKeyCommand` sends each command once through generated dispatch with redirects, replayable bodies and idempotency headers disabled. It accepts only 201/200 (published) or 202 (committed, publication unconfirmed: exit 0 plus a note on stderr) with a receipt that matches the operation. Server refusals keep their status and key. A follower's `503 primary_required` reads as "did not run; nothing changed" and carries the primary hint. A missing or unusable response is reported as an unknown outcome and is never retried. | The operator page told readers to keep secrets out of arguments but offered only hand-written JSON files for `kudurru api`, which left the secret in a request file and the receipt statuses unexplained. The single-attempt shape follows the RoleBinding and integration commands. | A `--secret` flag (puts the secret in argv and shell history). Generating the secret on the server and showing it once (the API takes a secret the operator already shares with peers; a server-generated secret would need a new API contract). Routing through `kudurru api` with a helper that writes the JSON (still a secret file on disk). Retrying on 503 (D357/D362: no replay of an uncertain mutation). |
