| D373 | G22 scope: final artifact, upgrade source, mixed versions, and stored objects of 0.1.0 that 0.2 cannot serve | (1) The final built artifact is the CGO-disabled release build of the final head (`make build`, the Dockerfile image): the binary `KUDURRU_E2E_BINARY` names. Licensed multi-node scenarios qualify on the same source built with `-tags licensetest`, which adds one trusted test public key and nothing else (`KUDURRU_E2E_LICENSED_BINARY`); every recorded run names its binaries with version, checksum and build tags. (2) v0.1.0 (tag commit `89c59f89`; `state.db` schema 1, `querylog.db` 2, `local.db` marker 1) is the only supported upgrade source. Upgrade evidence starts from bytes written by a 0.1.0 binary: built from the tag at test time outside the working tree (`kudurrutest.Previous`, or the published binary in `KUDURRU_E2E_PREVIOUS_BINARY`), and two committed golden `state.db` files written by it in the same tests. Rows written by current code at an old schema number are not upgrade evidence. Downgrade is not supported: every database refuses a newer schema and names the file. (3) Mixed versions are refused, not bridged: schema 9 is the first that can enroll, so no older enrolled SQLite peer exists, and replication requires the exact `StoreSchemaVersion` and every required feature. Static twins upgrade host by host. Kubernetes 0.1 to 0.2 is an offline upgrade whenever private IAM Secrets or HMAC AuditLog batches exist, and rolling otherwise. (4) SQLite refuses to upgrade a database that holds a stored object this release refuses to write. The last step of the `state.db` migration, inside its transaction, checks every stored object as the complete serving image will (strict decoding, the current CRD schema or the kind's own validation, and the DNSZone rule below); one failure rolls the transaction back and the process exits naming every such object. The database stays byte for byte as 0.1.0 wrote it, 0.1.0 still runs on it, and the operator corrects the objects there. The same DNSZone rule is write admission on SQLite: a zone the image cannot build or the primary runtime cannot commit (a type no release serves; a query, transfer or notify policy that does not compile; a primary `spec.policy.update` other than `deny` or `allow`; the zone name of another DNSZone; a new object name for the apex of a deleted zone whose ZoneLifecycle is still kept) is refused as `invalid` with its field (`zone.ServingErrors`, which asks the image's own builders; the name and lifecycle checks run in the write transaction, each on its own index). What one part of an object cannot contribute is left out and reported instead of failing the image, as 0.1.0 did: a record set that names a forward zone; an endpoint the primary builder refuses (CNAME next to other data, apex CNAME or NS), withheld from the commit with its reason; a block list source whose fetch failed before any body arrived (status error, no digest), compiled empty while the list reports the failure. The serving publisher logs why a generation is not published. | Executed with the released binary, not read from code: a 0.1.0 data directory holding one secondary or stub zone without its configuration, one `external` zone, a second DNSZone for a zone name or one free-form policy rewrite (all accepted by 0.1.0, which reported them on the object) was migrated to schema 9 and then served nothing: SERVFAIL for every name, readiness 503 and every API route 503 `generation_pending`, with no log line naming the object, no API left to correct it and no way back, because 0.1.0 refuses schema 9. The same outage followed on 0.2 alone from one accepted `POST` of such a DNSZone, or of an ordinary record set on a forward zone. The review of the first cut found four more with the released binary: a block list with a dead URL (nothing served, API 503, also on 0.2 alone), a record set with an apex CNAME, apex NS or CNAME next to an A (zone never served after the upgrade, never ready), `update: useNetworkACL` (zone never committed) and a zone re-created under another object name (the image refuses the kept Retired lifecycle next to the new one: node down). Refusing a record set or a block list that is valid in the schema would turn an outside event (a URL going away) or an ordering accident into a write the operator cannot make, so those are left out of the image part they cannot fill instead. The serving image is complete or absent by design and the API authenticates against a published image, so an object the image cannot carry can only be stopped before it is stored; an upgrade that finds one can only stop before it commits. | Migrating and leaving the objects out of the image (changes image completeness, manifests and digests); validating stored objects with ratcheting tolerance (the compilers assume the tightened invariants, and the zone rules are not schema); deleting or rewriting the objects during migration (D326: never repair; silent loss of operator data); making the image carry an unbuildable zone as unavailable coverage (an unsupported configuration must not keep an earlier usable zone silently); a dry run of the complete image preparation before every commit (inverts the publication-then-store lock order and doubles preparation); current-code rows at an old schema number, or published container images, as the upgrade baseline; a production-signed multi-node license run as a gate (owner-only); refusing the upgrade for a never-downloaded URL list or a refused endpoint (both valid objects, and the URL can fail after any upgrade); deleting the Retired lifecycle when a new object claims its apex (lifecycle transitions are owned and CAS-checked by the primary runtime, and the store never rewrites them; a later package may let a retired lifecycle release its apex) |
