# HA-AUTH-SETTINGS decision row (complete corrected D368)

This replaces the D368 row drafted in out/HA-REFUSAL/decision.md. Only the forwarded-domain sentence, the reason and the rejected alternatives changed.

| D368 | The v0.2 follower contract: forwarded domains, local commands and one typed refusal | Every API operation with an unsafe method has one follower class, kept by operation ID in one table (`internal/api/follower.go`) and published as `x-kudurru-follower`. `forwarded`: the follower sends one typed member command and relays the primary's answer. The forwarded domains of v0.2 are the blocking switch (D357), canonical object writes and the four zone convenience commands (D362), local password login (D363), sign-out with own-session revocation (`auth.logout`: `POST /auth/logout`, `POST /auth/logout/browser`, `DELETE /auth/sessions/{id}`) and the cluster settings patch (`settings.patch`: `PATCH /settings`); self-service password and tokens, allow/deny domain commands and unblock decisions may follow the same way. Both new commands follow D362/D363: the follower bounds the route to 30 seconds before body read, admits the credential against its leased view, captures its source once and sends one version-2 command with the raw credential proof; the primary verifies that credential again in the member transaction, where effect, audit and dedup commit together; clean refusals are retained results; an unsent command answers `503 unavailable`, a failed exchange `503 completion_unknown`; nothing is retried. `auth.logout` revokes the session that the primary itself derives from the verified cookie (`AuthenticateCurrentSessionWithClock`), never a claimed one; a token or JWT caller revokes nothing; `DELETE /auth/sessions/{id}` keeps the route's owner check and a retained `404`; a credential the primary no longer accepts is a retained `401`, except that a command whose dedup record exists is aborted so that a revoked credential never recovers its own retained outcome; the result is emitted under the command scope only (no credential lifetime), because the command may revoke its own credential; no audit row is added, as on the primary's own route. On the follower a sign-out always clears the browser's cookies, also when it was not sent or its outcome is unknown, and then says that the session may stay valid until it expires; a successful one pulls once so that the follower refuses the session at once; a follower offers no provider logout continuation. `settings.patch` carries the merge patch, the If-Match and an unstored random nonce, with the resourceVersion of `Kudurru/default` in the follower's view as precondition (a stale one is a retained `409 conflict`); the primary runs `ForwardedSettingsCommand`, which repeats the route's key, scope, lock and value checks, merges into the transaction's singleton, checks branding against the transaction's pinned license (`deps.License`, again at commit) and stages one write whose object audit row carries the original caller; refusals before the write (`400`, `402`, `409`, `412`) are retained and a failed write rolls back; the follower pulls once and answers with the primary's body under its own node name when its published view no longer carries the precondition version (at most five seconds; a failed pull or late publication still answers the commit), so that the caller's next change or blocking switch through it is not refused as stale, and the settings schema no longer marks cluster keys read-only on a follower. `PATCH /node/config` stays `primary`. `local`: the node's own response cache, query log, resolver and DHCP server, the cluster commands that decide from the node's own role (promotion runs on a follower; activation and invitations keep their `409`), and the two legacy settings-ownership routes that refuse on every SQLite node. `primary`: everything else, and every operation that the table does not name, including the two import previews, which write nothing but plan an apply that only the primary runs (the decommission preview's revision is the primary's resourceVersion that the decommission checks). A `primary` operation is refused on a follower by a route middleware attached where routes are declared, after authentication and the permission check and before the body is read: `503 primary_required`, with the primary's name, a hint and no `Retry-After`. The role is that of the request's own source (the authority its lease captured before authentication), never a later sample. The writer seams (`currentAuthCommandThen`, `currentAuthCommandOutput`, `MigrationCommand`) and the provider-login admission answer the same key when a follower's request reaches them without passing the router. `kudurru login --username` reads `GET /auth/status` first and refuses on a follower before it sends the password, because the forwarded login would leave a session on the primary that the refused token step cannot use. `GET /cluster` reports `role`, `primary`, `primaryRequired` and the operation IDs of the forwarded and local classes; the settings schema marks a key read-only when its PATCH would be refused; a follower's `GET /auth/status` carries `role` and `primary` and lists no OIDC provider; the follower's block page replaces the unblock form with a message. `POST /cache/flush` runs on a follower without a transaction, authorized against the request's leased authentication view. A fenced or conflicted member, whose API is closed, answers `503 cluster_fenced` or `503 cluster_conflict` with a hint and no `Retry-After`, from the lease adapter (after its bounded capture wait) and from the provider-login admission alike; `generation_pending` with `Retry-After` remains for a publication that is being prepared. | A follower answered every unforwarded mutation with the generic `503 unavailable`, "current writable serving generation unavailable", the same text as a transient publication gap, and a list refresh answered `202` although nothing fetches on a follower. V2-HA requires that read-only and fenced status and forwarding failures are explicit. D362 rejected a generic reverse proxy and forwarding without typed domains, and D300 is the precedent for a typed refusal that UI capabilities reflect. A default at the route-declaration layer cannot be missed by a route added later: it is refused until a reviewed line classifies it, an inventory test fails for a registered mutation without a line, and a mounted follower test requests every registered mutation. The role comes from the request's lease because the original-source rule forbids deciding from a replacement source. Dropping `Retry-After` keeps clients from retrying a state that only an operator, a promotion or the next pull ends. Sign-out is forwarded rather than refused because D363 lets a follower create sessions, and a session that cannot be ended where it was created is a correctness defect; settings is one route with a transaction-level plan seam and the first domain the tracker names. | A generic HTTP proxy to the primary (rejected in D362); per-route edits or a refusal only at the writer seams (a route that never opens a writer transaction, such as list refresh, is missed, and a new route is forwarded or refused by accident); a refusal in the HTTP middleware before route matching (answers before the permission check and for paths that are no routes); `409 conflict` or `421` (every mutating operation already documents `503`, and `read_only` is the precedent); a capability by RBAC resource and verb (`blocklists.write` covers both a forwarded editor route and the refused allow/deny commands); reporting `fenced` on `GET /cluster` (a fenced or conflicted member serves no API request, so the field could never be true); forwarding node log settings (the primary's row is not the follower's) or forwarding a cache flush (it would flush the wrong node); keeping `generation_pending` with `Retry-After: 1` for a durable conflict; refusing sign-out on a follower and clearing only the cookie (the durable session would survive); revoking a session ID that the follower names for a sign-out (the primary derives it from the verified cookie); aborting the exchange for a credential the primary no longer accepts (reports `completion_unknown` for a clean answer); merging a forwarded settings patch into the primary's current settings without a precondition (could overwrite values the caller never saw) or forwarding the follower's merged values (stale map leaves); an extra `settings.write` row in the primary's chain (the object audit row in the same commit already attributes the change); reading the Store's current authority to decide a request that already holds a lease; classifying the import previews as `local` (their plan would come from a replica that may lag the primary that applies it) |
