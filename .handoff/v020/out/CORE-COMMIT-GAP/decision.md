| D395 | Answering zones across canonical commits | (1) The silence after an unrelated commit that QUAL-OPEN3 measured (up to 586 ms) was measured at `d2039002`, which does not contain D378 (`10d3ab5b`); D378 already binds ordinary local, authoritative and mixed answers to the served publication instead of the latest commit, and at the lane head an unrelated BlockList create or delete left no probe unanswered beyond a single query (CORE-COMMIT-GAP `measure01`). Two causes remained, both found with direct 5 ms UDP probes on a mounted node and instrumented refusals. (2) A write of a zone's own `DNSZone` (query ACL, name servers, selector) made every publication serve the zone as committed-unavailable coverage until the driver had refreshed its lifecycle receipt and, for a primary, committed a head of the new configuration: SERVFAIL for up to about 0.3 s, primary and forward zones alike. `PreparedImage.Serves` now keeps the same zone (same name, UID, apex and type, a source that is not removed, an active lifecycle and head) in DNS routing through that gap: a primary answers its last committed head under the query access mode and ACL of the new configuration (`zone.RetainCommittedPrimary`) with zone transfers refused, and a nonprimary answers its new configuration, from which its model is always built. `PreparedImage.Admitted` stays strict, so UPDATE, NOTIFY, status projection, publication acknowledgment and integrations still wait for the driver; a deleted, replaced or retyped zone, an inactive head and expiry still get coverage. (3) A query whose publication was replaced between capture and output had its answer withheld with no reply (about one query in a few thousand per swap). `Publisher.ServedWithin` now recognizes the last eight replaced publications for a bound of one second (`servedSuccessorGrace`) after the swap that replaced each, however many swaps followed; the record holds weak pointers, it is written before the pointer swap so that a reader always finds a leased publication either current or retired, and a DNS-only (fenced) publication (cleared before the fenced swap) or `Close` clears it. (4) Whether the 1.39 s DNS gap of CORE-OPEN3 `run05` has this cause is not determined: it was not reproduced, and one withheld query explains about 0.3 s of gap with that probe (200 ms timeout plus 50 ms sleep), not 1.39 s (five or six consecutive losses, against a measured rate of about one query in a few thousand per swap); a server-side stall of more than 200 ms per query is at least as likely, and the grace would not fix that. | Every such answer is committed data: `Capture` only returns the served publication, so the query was received while its data was current, and the answer is what the client would have got a moment earlier. The one-second bound is a staleness bound, not a window of silence: no query captured after a swap can use the old publication, and an answer from a replaced publication is sent at most one second after its replacement. The safety properties are unchanged: nothing is answered from data that was never committed; nothing qualifies across a fence; the DNS dependency installations (keyring, transferred and catalog zone data, root lifetime) and the anchor input are still checked at the handoff; transfers, UPDATE acknowledgments, API dig, cache insertions and native resolver mutations keep full data currency; a tightened query ACL applies from the first publication after the write. Measured after the change without the race detector: 0 of about 41,000 probes per zone unanswered or SERVFAIL across 5 runs of 28 writes (and 0 in 3 runs under the race detector), and 0 failures in every window of the QUAL-OPEN3 harness. | Accepting the window as designed (the draft in QUAL-OPEN3); turning a withheld answer into SERVFAIL (still a failed answer); waiting in DNS for the next publication (puts publication latency on the query path); a grace only for the immediate predecessor (a query can outlive two swaps a few milliseconds apart; that draft still lost one probe in three runs, cause not captured); an unbounded grace or one keyed on publication count rather than time (no staleness bound); keeping the zone admitted for every purpose in the config gap (UPDATE and NOTIFY would act on a head of the old configuration) |
